# epic AI 작업 지침

## 목적

갱신된 `spec/`을 기획/PM/오케스트레이터, 개발자 3명, Artist 3명과 통합 QA·릴리스가
독립적으로 수행할 수 있는 순차·병렬 작업으로 유지한다.

## 작업 상태

- `대기`: 아직 구현을 시작하지 않음
- `진행 중`: `app`에서 구현 중
- `완료`: 완료 기준과 검증을 충족함
- `보류`: 외부 결정 또는 선행 작업을 기다림
- `변경 확인 필요`: 진행 중 요구사항이 바뀌어 담당자가 새 범위를 확인해야 함

## spec 변경 반영 규칙

1. 변경된 요구사항 식별자를 참조하는 모든 작업을 찾는다.
2. 변경된 `spec/`의 이전·새 문서 버전을 확인한다.
3. `대기` 작업은 목표, 범위, 절차와 완료 기준을 즉시 갱신하고 태스크 문서 버전을 올린다.
4. `진행 중` 작업은 변경 내용을 즉시 반영하고 상태를 `변경 확인 필요`로 바꾼다. 태스크 문서 버전을 올리고 변경 이력에 추가·삭제·재작업 범위를 분명히 적는다.
5. `완료` 작업은 수정하지 않는다. `v1.0.0`의 후속 작업을 새 순번으로 생성하고 기존 작업을 선행 작업으로 연결한다.
6. 관련 작업이 없거나 기존 작업의 독립성을 해치는 변경은 `v1.0.0`의 새 작업으로 만든다.
7. 두 개발자의 파일을 동시에 변경할 때 의존성과 인계 조건을 각각 명시한다.

새 작업은 `template/epic_작업_템플릿.md`를 사용한다.
버전 증가는 `template/spec_epic_문서_버전_관리_지침.md`를 따른다.

## 작업 현황 동기화

`작업_현황.md`는 기획/PM/오케스트레이터, 개발자 3명, Artist 3명과 통합 QA·릴리스의 전체
태스크를 집계하는 대시보드다.

- 태스크 생성, 상태 변경, 담당자 변경 또는 삭제 시 반드시 같은 변경에서 갱신한다.
- `진행 중`과 `변경 확인 필요`는 담당 개발자의 현재 수행 작업으로 표시한다.
- `대기`, `보류`, `완료`는 각각의 표에 표시한다.
- 상단의 전체 개수와 상태별 개수는 실제 태스크 문서와 일치해야 한다.
- 대시보드를 변경할 때 수 버전을 올리고 변경 이력에 동기화 내용을 추가한다.
- 상세 목표와 작업 절차를 대시보드에 복제하지 않고 태스크 문서를 연결한다.

## 담당 배정

- `pm-orchestration/`: 스테이지 임계경로, 역할 서브에이전트 run, 사용자 승인 큐, 완료 뒤 자동
  인계, 사람 화면 테스트와 stage 완료 판정 중심
- `developer-1/`: 핵심 시스템, 게임플레이, 런타임 구조 중심
- `developer-2/`: UI, 콘텐츠, 시나리오, 아트·오디오 연동 중심
- `developer-3/`: 밸런스 데이터 파일·로더·검증, 개발·기획용 도구(튜닝 UI·로직 시뮬레이터) 중심
- `qa-release/`: 역할별 변경 통합 기준선, 자동·수동 회귀, 에셋 handoff와 공개 gate 검증 중심
- `artist/`: Artist 1·2·3의 브랜드, 환경, 캐릭터, 3D 조작물, 음식, UI icon, VFX 제작과 에셋 manifest·개발자 카탈로그 관리
- 경계가 겹치면 각자 독립적으로 완료 가능한 단위로 나누고 입출력 계약을 두 작업에 동일하게 기록한다.
- `developer-1`의 게임 로직은 수치를 데이터에서 읽고, `developer-3`가 그 데이터 파일·검증·도구를 제공한다. 두 역할은 데이터 스키마(`DAT-001`)를 공통 계약으로 삼는다.
- Artist는 제작·검수 상태를 `art-workspace/ASSET-CATALOG.md`에 기록한다. 최종 runtime
  승격은 `app`의 자동 게이트로만 수행하며 `app/public/assets/manifest.json`을 런타임
  단일 원본으로 유지해 개발자가 추측한 경로를 만들지 않게 한다.
- Artist 1·2·3은 같은 stable asset ID, `sourceMasterId`, semantic state 또는 finalizer bundle을
  동시에 수정하지 않는다. 각 태스크의 소유권 표에 단일 `semanticOwner`와 review namespace를
  기록하고, 다른 Artist의 승인 원본은 읽기 전용 합성 입력으로만 소비한다.
- 현재 기본 분담은 Artist 1이 D1 조립·그릴 음식과 shader 상태, Artist 2가 S0와 이야기·초상,
  Artist 3이 D1 드링크·서빙·정리·엑스트라·정산 및 후속 D2~D3 서비스 아트를 맡는 것이다.
- 개발자는 screen/state/component/requiredAsset ID 목록을 먼저 고정해 Artist에게 제공하고,
  Artist는 파일명이나 상태 ID를 추측하지 않는다. 승인 상태는 소비 화면 FHD/720 재조립,
  최적화, 최종 승인과 finalizer handoff까지 끝난 뒤 개발자 2의 승격 절차로 전달한다.
- 통합 QA·릴리스는 기능·아트 의미를 수정하지 않고 결함의 재현·분류·소유자 배정·재검증만
  담당한다. 다른 역할의 dirty 파일을 정리하거나 승인·manifest 상태를 대신 변경하지 않는다.

## PM 오케스트레이션 규칙

- PM은 역할 agent의 완료 보고를 실제 diff·artifact SHA·완료 기준·테스트와 대조한 뒤에만
  epic과 dashboard를 갱신한다.
- 사용자 승인 없이 진행 가능한 후속 consumer가 있으면 완료 동기화 뒤 즉시 자동 인계한다.
- 사용자 승인 lane은 해당 branch만 멈추고 충돌 없는 독립 lane은 계속한다.
- PM·QA는 아트·시나리오·실제 소비 화면을 자기 승인할 수 없다.
- 같은 파일, stable asset ID, sourceMasterId, semanticOwner, finalizer, manifest promotion은
  동시에 한 writer만 가진다.
- 자동 테스트와 별도로 각 스테이지 중간 slice와 전체 구동 화면을 사람이 직접 조작해야 한다.
  사용자가 `PASS`하기 전에는 PM stage 태스크를 완료로 바꾸지 않는다.
- S0와 D1은 병렬 제작하되 두 stage가 모두 완료돼야 최초 공개 gate가 닫힌다. D2는 D1 뒤,
  D3는 D2 뒤에 순차 활성화한다.

## 금지 사항

- 요구사항 근거가 없는 작업 생성
- 완료 작업의 범위 또는 완료 기준 변경
- 같은 순번 재사용
- `app` 소스코드나 구현 결과물을 `epic/`에 저장
- 태스크 변경 후 `작업_현황.md`를 이전 상태로 방치
- 기존 태스크를 변경하고 문서 버전 또는 변경 이력을 갱신하지 않음
- 사용자 `PASS`가 없는 stage를 온전히 구동 완료로 기록
