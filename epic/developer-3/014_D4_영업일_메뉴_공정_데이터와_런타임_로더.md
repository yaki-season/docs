D4 release data 하나가 메뉴·station·공정·8주문·경제·완료 보상의 정본이 되게 한다.
Developer 1은 수치를 코드에 복제하지 않고 loader 결과만 소비하며, 자동 schema 검증 결과는 데이터
오타를 찾는 보조 신호로만 사용한다. 실제 적용 여부는 Developer 2 화면과 사람 전체 플레이에서 확인한다.

## 범위

- 사라다의 주문 필수·단독 주문 금지·수량 1~2·만족도 제외·접시당 10초 대기 회복 metadata
- `highball` 메뉴의 `stationId=drink`, `basePriceG=7`와 품질별 7/4/2/1G 결과

- `day-d4`의 8명·8개 개별 주문·19항목, 2인 그룹의 서로 다른 order ID, 활성 주문·위험 공정 2/2
- D4 완료의 `day-d5`·`kawa` 해금과 D6 기능 비활성
- `d4-preview`를 실제 `d4`로 전환하는 campaign content version·구형 save migration 입력
- 날짜 중립 definition loader 또는 D4 loader와 명시적 오류 결과
- D4 content가 UI에 제공할 station/menu descriptor와 recipe-note copy key

## 작업 절차

1. 현재 `early-campaign.json`, `d3-business-day-domain.v1.json`, day/menu/order schema와 D1~D3 loader의 중복 필드를 목록화한다.
2. 메뉴 fulfillment와 station process를 날짜 data에서 참조할 수 있는 schema를 추가하되 D1~D3 record는 기본값으로 호환한다.
3. 사라다·하이볼 menu/process record를 만들고 GPL-006 수치를 한 곳에서만 정의한다.
4. `D4-ORDER-001~008`을 개별 customer/order로 작성하고 총 `8/8/19`와 그룹 인접 조건을 release artifact에 명시한다.
5. campaign chain을 `d3→d4→d5` 준비 상태로 갱신하고 기존 `d4-preview` save를 Developer 1이 해석할 migration descriptor를 제공한다.
6. D5는 해금·pre-open 경계까지만 노출하고 gameplay availability를 명시적으로 막아 미구현 영업이 시작되지 않게 한다.
7. loader가 menu/process/day record를 합성해 Developer 1에게 불변 view를 반환하고, 오류는 silent fallback 없이 식별 가능한 code로 반환한다.
8. 자동 schema·합계·교차 참조 검사는 보조 진단으로 실행한 뒤 Developer 2 실제 화면에서 주문명·수량·공정 수치가 소비되는지 사람이 확인한다.

## 병렬·순차 계획

- 다른 역할과 병렬 가능한 범위: Developer 1 작업 018의 domain interface, Artist 027의 콘셉트 연구
- 반드시 순차로 진행할 범위: schema·ID 동결 → D4 release record → loader handoff → Developer 1 runtime 소비 → Developer 2 화면·사람 검수
