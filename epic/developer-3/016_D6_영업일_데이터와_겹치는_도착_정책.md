# 개발자 3 - 016 D6 영업일 데이터와 겹치는 도착 정책

- 상태: `대기`
- 담당자: `개발자 3`
- 우선순위: `P0`
- 현재 milestone에 필요한 이유: D6 release 정의가 없고, 현재 영업일 데이터는 모든 파동이 앞 주문 완료를 기다리는 형태라 첫 만석을 만들 수 없다.
- 하지 않으면 막히는 stage gate: D6 주문표·상한 확정, Developer 1의 도착 정책 구현, D6 전체 플레이

- `spec/data/DAT-001_콘텐츠와_밸런스_데이터_계약.md` - `DAT-001`

## 목표

`GPL-007`의 D6 주문표를 release 데이터로 확정한다. 파동이 앞 파동의 주문 완료가 아니라 시각으로 도착하도록 데이터 형태를 정하고, `maxActiveOrders=3`을 D6에만 적용한다. 신규 메뉴를 추가하지 않으므로 메뉴·레시피 데이터는 건드리지 않는다.

## 범위

### 포함

- `content/releases/d6-business-day-domain.v1.json` 신설: 손님 10명·주문 10건·항목 22개
- 파동 5개의 `atMs`와 빈 `requiresOrderCompletionIds` 구성
- `limits.maxActiveOrders=3`, `limits.maxRiskProcesses=2`
- 항목 22개의 메뉴별 배분 확정. 꼬치 12개 이하, 그릴과 드링크가 함께 돌도록 구성
- 캠페인 chain에 D6 노드 추가와 `day-d6-completed` 보상 레코드
- D6 정의가 D7 콘텐츠를 참조하지 않는다는 로더 검증

### 제외

- 도착 판정 로직 자체 — Developer 1 작업 020
- 좌석·말풍선 표시 — Developer 2 작업 017
- 신규 메뉴·레시피·조리 임계값. D6는 어느 것도 추가하지 않는다
- D7 데이터

## 작업 절차

1. `GPL-007` 주문표를 D4·D5 release와 같은 스키마로 옮기고 파동별 `atMs`를 정한다.
2. 항목 22개를 해금 메뉴 안에서 배분하고 꼬치 12개 상한을 검증으로 고정한다.
3. `requiresOrderCompletionIds`를 비운 파동이 스키마를 통과하는지 확인하고, 필요하면 스키마의 필수 여부를 완화한다.
4. `maxActiveOrders=3`이 D6에만 적용되고 D1~D5 정의가 바뀌지 않는지 회귀로 확인한다.
5. 캠페인 chain에 D6를 추가하고 D5 완료가 D6 pre-open으로 이어지는지 확인한다.
6. Developer 1에 도착 판정에 필요한 입력(파동 시각, 상한, 좌석 요구 인원)을 인계한다.
