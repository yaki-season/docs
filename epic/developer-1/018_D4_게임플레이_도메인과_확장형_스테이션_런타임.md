## 목표

기존 D1~D3 동작을 유지하면서 D4의 사라다 준비·서빙, 하이볼 제조·품질, 공용 준비 목록,
8주문 영업과 저장 전이를 순수 domain과 application controller로 구현한다. 현재 2,879줄
`d1-game.js`에 D4 상태 머신과 날짜별 조건문을 추가하지 않고, 이후 즉시 제공 메뉴와 음료 작업면을
데이터·registry 등록으로 확장할 수 있는 경계를 만든다.

## 범위

### 포함

- D1 명칭에 묶인 공용 business-day runtime의 점진적 일반화와 기존 import용 호환 wrapper
- 메뉴별 `basePriceG`, `qualityMode`, `satisfactionWeight`, `waitRecoveryMs`, `requiredForCompletion` 소비
- `cabbage-salad`의 0G·무품질·만족도 제외·주문 완료 필수·접시당 대기 10초 회복
- `highball`의 얼음→두 액체→레몬, 병 hold, 4.8 units 넘침, 폐기/저품질 제공과 품질 판정
- 위스키·탄산수 상태를 서로 독립적으로 누적하고 레몬 전까지 반복 보충하는 한 잔 controller
- 화면 전환·일시정지·blur·pointer cancel에서 hold 상태를 취소하거나 보존하는 명시적 정책
- 메뉴 ID·품질·zone 기반 공용 준비 inventory와 기존 label 추론 제거
- runtime snapshot version 갱신, D1~D3 구형 snapshot 호환과 D4 미완성 작업면 복구
- D4 drain·정산 단일 적용·D5와 토리카와 해금에 필요한 campaign transition
- Developer 2가 DOM·Three.js에 연결할 입력 command와 읽기 전용 view model

## 작업 절차

1. `d1BusinessDay.js`의 판매·품질·만족도 계산과 `preparedDock.js`의 한글 label 추론이 D4 계약을 깨는 지점을 실제 호출 경로로 고정한다.
2. 기존 API를 깨지 않는 호환 wrapper를 남기고 날짜 중립 business-day aggregate와 menu fulfillment policy를 분리한다.
3. 준비 inventory의 정본을 `menuId/quality/zone` 기반 application state로 옮기고 presentation dock은 view만 소비하게 한다.
4. `createInstantServiceStation` 계열 controller를 메뉴 catalog 기반으로 구현해 `2.5초=1접시`, 자동 반복 금지와 모든 취소 조건을 단조 증가 시간으로 판정한다.
5. `createHighballMix` 계열 순수 상태 머신에 glass·ice·whiskey·soda·lemon·overflow·discard·finalize를 구현하고 수치를 데이터에서 주입받는다.
6. 드링크 상위 controller가 `beer`·`highball` 작업면을 registry로 소유하고, 미완성 잔이 있을 때 내부 모드 변경만 거부하며 다른 station 이동은 허용한다.
7. D4 주문 제공 시 사라다는 sale·quality metric을 만들지 않고, 유료 품질 항목만 만족도 평균에 포함하도록 aggregate를 수정한다.
8. snapshot migration과 campaign의 `d4-preview→d4` 전환 호환을 구현하고 Developer 2·3에 view model·command·schema handoff를 준다.
9. 자동 검증은 계산·중복·migration의 빠른 회귀 신호로만 사용하고, Developer 2 graybox에서 사람이 첫 주문을 실제 입력으로 완료해 contract를 확인한다.
