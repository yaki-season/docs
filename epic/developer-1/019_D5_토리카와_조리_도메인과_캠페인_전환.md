# 개발자 1 - 019 D5 토리카와 조리 도메인과 캠페인 전환

- 상태: `진행 중`
- 담당자: `개발자 1`
- 우선순위: `P0`
- 현재 milestone에 필요한 이유: 현재 공용 조리 런타임은 굽기 경계를 전역 상수로 사용하고 타레 마감을 `momo`에만 하드코딩하며, 캠페인은 `d5-preview`에서 끝나므로 확정 D5 토리카와를 올바르게 표현할 수 없다.
- 하지 않으면 막히는 stage gate: 토리카와 조립·품질·타레 마감, D5 정산·저장과 D6 비노출

## 목표

기존 D1~D4 결과를 유지하면서 메뉴별 recipe/process policy를 주입받는 공용 조리 domain을 만들고,
`kawa`의 5회 조립·면별 `10/14/18초`·소금·타레·선택적 토치를 구현한다. D4 완료 저장은 실제
D5 pre-open으로 이관하고 D5 완료는 `day-d5-completed`만 멱등 저장한다.

## 범위

### 포함

- 조립 sequence와 `repeatSameIngredientClick/nextEmptySlot`을 메뉴 데이터로 소비하는 공용 aggregate
- 메뉴별 `faceThresholdsSec`·양면 품질 테이블 주입과 전역 `COOK_THRESHOLDS_SEC` 의존 제거
- `kawa` stable ID·`salt|tare`에 대한 굽기·회수·완전 탄 폐기 규칙
- `momo` 전용 분기를 메뉴별 finish policy로 일반화하고 D3 타레 도포·재가열·토치 상태를 재사용
- 타레 2회 완료 뒤 토치 없이 회수, 시작한 토치는 완료 강제, 불향 보너스 분리
- 기본 양면 굽기와 타레/토치 마감 중 낮은 등급을 선택하는 최종 품질 집계
- 조립·그릴·마감 도중 pause·화면 이동·새로고침 snapshot 복구와 구형 D1~D4 snapshot 호환
- `d5-preview` 구형 저장을 실제 D5 pre-open으로 이관하는 campaign migration
- 계획 주문 drain·손님 퇴장·좌석 정리·토리카와 1개 이상 제공·정산 1회의 D5 완료 조건

### 제외

- D5 JSON·schema·loader 정본 — Developer 3 작업 015
- DOM·Three.js·레시피 노트·아트 binding — Developer 2 작업 016
- 토리카와 PNG 제작·승격 — Artist 1 작업 028
- D6 부채와 이후 gameplay

## 작업 절차

1. `cookStations.js`의 전역 경계와 `d3GrillSession.js`의 `menuId === 'momo'` 분기를 characterization test로 고정한다.
2. recipe assembly, bilateral grill, finish policy와 final quality reducer를 분리하되 기존 public API에는 호환 wrapper를 남긴다.
3. Developer 3의 D5 definition에서 조립 sequence·굽기 경계·finish policy를 주입하고 `kawa` 코드 분기를 최소화한다.
4. 타레 모모와 타레 토리카와가 같은 공통 도포·재가열·토치 로직을 사용하도록 만들고 각 메뉴의 선택 정책만 데이터로 구분한다.
5. 진행 중 조립·양면 시간·타레 횟수·토치 상태를 snapshot에 포함하고 구형 snapshot을 안전하게 migration한다.
6. campaign chain을 D4→D5 실제 day로 바꾸고 구형 `d5-preview` 저장을 D5 pre-open으로만 이관한다.
7. Developer 2에 command/view model과 실패 reason을 인계하고 구현자가 graybox에서 소금·타레 경로를 직접 플레이한다.

## 병렬·순차 계획

- 다른 역할과 병렬 가능한 범위: Developer 3 작업 015의 D5 content/schema, Artist 1 작업 028의 reference 분석
- 반드시 순차로 진행할 범위: D5 process schema 동결 → domain 일반화 → Developer 2 결선 → 실제 조작 확인 → D5 completion 통합
