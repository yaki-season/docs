# 개발자 1 - 007 영업일 루프 게임 로직 골격

- 상태: `완료`
- 담당자: `개발자 1`

## 참조 spec

- `spec/gameplay/GPL-002_30일_캠페인과_영업일_루프.md` - `GPL-002` - `v1.0.0`
- `spec/gameplay/GPL-003_주문_손님_좌석과_러시_운영.md` - `GPL-003` - `v1.0.0`
- `spec/data/DAT-001_콘텐츠와_밸런스_데이터_계약.md` - `DAT-001` - `v1.0.0`

## 목표

한 영업일 루프를 렌더링 없이 순수 상태로 구현한다. 영업 시작부터 손님 도착·주문·조리 연결·서빙·
퇴장 반복을 거쳐 영업 종료·정산 지표까지 도는 골격을 만들고, 수치는 코드 상수가 아니라 데이터에서
읽는다. 이 로직은 게임·시뮬레이터·자동 테스트가 함께 쓰는 단일 원본이 된다.

## 배경

아트(작업 005)와 최종 밸런스 수치가 확정되기 전에도 게임 로직은 만들 수 있다. 수치를 데이터에서
읽으면(작업 `developer-3/001`) `GPL-002`·`GPL-003`의 미해결 수치가 코드를 막지 않는다.
placeholder `candidate` 값으로 로직을 짜고 기획자가 도구(`developer-3/002`)로 조율한다.

## 범위

### 포함

- 영업일 루프 상태 모델: 영업 시작 → (손님 생성 → 주문 → 조리 연결 → 서빙 → 결과 집계 → 반복) → 영업 종료
- 렌더링·DOM과 분리된 순수 상태 함수. 모의 시간으로 구동
- 손님 생성과 주문을 데이터의 파동·간격 수치로 제어 (`GPL-002` 러시 파동 골격)
- 서빙 결과의 정산 지표 집계: 매출·팁·실패·이탈·평균 대기·품질 분포
- 기존 조리 상태(`gameState`)와 휴면 손님 로직(`src/state/customer/`)을 이 루프에 최소 연결
- 수치는 `developer-3/001`의 데이터·로더에서 읽음
- 무작위 요소의 시드 고정과 결과 재현성

### 제외

- 좌석 6석·2인 그룹·대기 게이지 가동·러시 우선순위의 완전 구현 (`GPL-003` 상세 → 작업 006)
- 30일 캠페인 진행·성장·해금 (`GPL-002` 캠페인 → 후속 작업)
- 2.5D 렌더링과 장면 (`작업 005`)
- 밸런스 편집 UI·시뮬레이터 (`developer-3/002`)
- 최종 수치 결정

## 작업 절차

1. 영업일 루프 상태 모델과 전이를 렌더링과 분리해 정의한다.
2. `developer-3/001`의 데이터·로더에서 손님 간격·조리 시간·인내심 등 수치를 읽어 연결한다.
3. 손님 생성 → 주문 → 조리 연결 → 서빙 → 결과 집계 반복을 모의 시간으로 구동한다.
4. 기존 조리 상태와 휴면 손님 로직을 이 루프에 최소 범위로 연결한다(완전한 좌석·그룹은 작업 006).
5. 영업 종료 시 정산 지표를 집계한다.
6. 시드 고정으로 결과 재현성을 보장한다.
7. 루프 전체를 모의 시간 자동 테스트로 검증한다.

## 의존성과 인계 조건

- 선행 작업: `developer-3/001_밸런스_데이터_파일과_로더_검증.md` 완료
- 후속 작업: `developer-3/002`(시뮬레이터가 이 루프를 재사용), `developer-1/006`(손님 좌석·그룹 상세),
  `developer-1/005`(이 로직을 2.5D 장면에 연결)
- 다른 개발자에게 제공할 입력·출력: `developer-3/002`에 영업일 루프 실행 API와 정산 지표 구조를,
  작업 005에 렌더링이 붙일 상태 전이 지점을 인계한다.

## 구현 및 검증 결과

- app 구현 위치
  - `app/src/state/businessDay.js` — 영업일 루프 로직(단일 서버 대기열, 자동 정책, 정산 집계).
    콘텐츠에서 config 생성(`buildConfigFromContent`), 판매가·팁 역할 분리(`revenueFor`/`tipFor`)
  - `app/src/state/customer/customer.js` — `baseJudge`를 공유 판정으로 분리(손님 엔티티·루프 공용)
  - `app/content/campaign/day-d1.json`, `content/schema/day.schema.json` — 루프 타이밍·자동 정책 수치 추가
  - `app/tools/simulator.js` — 정식 루프를 재사용하는 어댑터로 교체(dev-3/002의 "같은 로직 재사용" 충족)
  - `app/tests/unit/businessDay.test.js` — 콘텐츠 구동·재현성·수치 영향·역할 분리 9개
- 구현 기준 spec 버전: `GPL-002 v1.0.0`, `GPL-003 v1.0.0`, `DAT-001 v1.0.0`
- 구현 기준 태스크 버전: `v1.0.0`
- 검증 방법: `npm test`(영업일 루프 9개 + 기존 회귀). 실제 `content/`에서 config를 만들어
  손님 20명 처리·정산, 인내심↓→이탈↑·조리↑→이탈↑·성공률=1→과다 0·판매가만 바꿔도 팁 불변을 확인.
  튜닝 도구가 정식 루프를 재사용하고도 결과가 동일함을 브라우저로 확인.
- 검증 결과: `2026-07-23` 기준 단위 90개, 종단 회귀 통과
- 설계 반영 사항
  - 손님 판정을 `baseJudge`로 분리해 손님 엔티티와 영업일 루프가 단일 규칙을 공유한다(`SYS-005 §8`).
  - 판매가는 품질에, 팁은 대기 잔량·유형에만 반영해 `GPL-003`의 역할 분리(중복 가산 금지)를 코드로 고정.
  - 튜닝 도구 시뮬레이터가 이 루프를 재사용하도록 어댑터화해 두 시뮬레이터의 분기를 없앴다.
- 남은 위험
  - 이번은 **자동 정책 시뮬레이션** 경로다. 실제 플레이어 입력으로 구동하는 상호작용 루프(단계별
    tick·serve)는 2.5D 장면(작업 005)·손님 재정렬(작업 006)에서 연결한다. 계산 함수는 재사용 가능하게 분리해 뒀다.
  - 좌석·2인 그룹·대기 게이지 완전 구현은 작업 006이다. 이 골격은 단일 서버 최소 손님 모델이다.
  - `GPL-002`·`GPL-003`이 `초안`이라 러시 파동·정산 구조가 바뀌면 재작업이 있을 수 있다.
