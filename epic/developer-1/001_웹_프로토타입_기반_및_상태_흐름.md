## 목표

`app`에서 로컬 서버로 실행되는 웹 프로토타입 뼈대와 렌더링과 분리된 단일 주문 상태 흐름을 구축하고, 조립부터 서빙까지 필요한 모든 상태 전이를 자동 검증한다.

## 범위

### 포함

- 현재 `app/sources` 실험물과 기존 에셋의 재사용 가능성 점검
- 렌더러를 기존 WebGL2로 확장할지 Three.js로 전환할지 결정하고 한 경로로 정리
- 로컬 실행 명령, 애플리케이션 진입점과 기본 반응형 작업 영역 구성
- 게임 세션, 레시피 진행, 면별 시간, 결과와 재시작 상태 모델 구현
- `loading`부터 `failed`까지 상태 전이와 조리 경계 자동 테스트
- 브라우저 숨김·복귀 시 조리 시계 정지
- 안정된 테스트 선택자와 개발 모드 상태 관찰 지점

### 제외

- 완성된 조리 상호작용과 최종 아트 적용
- 생맥주, 스테이지, 점수, 저장과 서버 기능
- 배포, PWA와 앱 패키징

## 작업 절차

1. `app`의 기존 셰이더, 꼬치 텍스처, HTML과 도구 페이지를 조사하고 재사용·대체 목록을 기록한다.
2. 최소 의존성으로 로컬 실행·테스트 명령과 애플리케이션 진입 구조를 정한다.
3. 레시피와 조리 임계값을 한 위치에 정의한다.
4. 조립 인덱스, 공정, 앞·뒷면 시간과 판정, 선택, 성공·실패를 갖는 상태 모델을 구현한다.
5. 허용된 입력만 상태 전이를 만들도록 전이 함수를 구현하고 렌더링 코드와 분리한다.
6. 모의 시간을 사용해 모든 임계 경계와 성공·실패·재시작을 자동 검증한다.
7. 기본 화면에 로딩, 오류와 빈 작업 영역을 연결한다.
8. 실행 방법, 테스트 방법과 렌더러 선택 근거를 `app` README에 기록한다.

## 구현 및 검증 결과

- app 구현 위치
  - `app/src/state/gameState.js` — 상태 모델과 전이 함수 (순수 함수, DOM·WebGL 의존 없음)
  - `app/src/config/recipe.js` — 레시피와 조리 임계값의 단일 정의 위치
  - `app/src/main.js` — DOM 이벤트·렌더링 배선과 단일 `requestAnimationFrame` 루프
  - `app/src/index.html`, `app/src/style.css` — 진입점과 작업 영역 레이아웃
  - `app/src/render/grillRenderer.js`, `app/src/shaders/` — 익힘 셰이더 렌더러
  - `app/tests/unit/`, `app/tests/e2e/` — 자동 검증
  - `app/README.md` — 실행·검증 명령, 렌더러 선택 근거, 재사용 판정
- 구현 기준 spec 버전: `SYS-001 v1.0.0`, `UI-001 v1.0.0`, `GPL-001 v1.0.0`
- 구현 기준 태스크 버전: `v1.0.0`
- 검증 방법
  - `npm run verify` — 단위 테스트(Vitest)와 종단 테스트(Playwright, Chromium)를 연속 실행
  - 조리 판정 경계 6개는 `2.5`, `5.5`, `7.0`초의 직전·직후를 모의 시간으로 검증
  - 숨김·복귀는 `visibilityHidden`/`visibilityVisible`에 모의 시간을 넣어 검증
- 검증 결과: `2026-07-21` 기준 단위 31개, 종단 8개(`1280×720`, `1920×1080` 각 4개) 전부 통과
- 렌더러 결정: 기존 WebGL2 유지. Three.js 미도입. 3D 대상이 그릴 위 꼬치 하나뿐이고
  기존 익힘 셰이더를 수정 없이 옮길 수 있어 통합 비용이 가장 낮았다. 근거는 `app/README.md`에 기록.
- 남은 위험
  - 헤드리스 종단 테스트는 GPU가 없어 SwiftShader 소프트웨어 렌더링을 사용한다. 성능 관련
    비기능 요구사항(30 FPS)은 이 경로로 검증할 수 없고 작업 004의 실제 브라우저 확인이 필요하다.
  - 화면 구성은 플레이스홀더 도형이며 실제 에셋 적용은 작업 003 범위다.
