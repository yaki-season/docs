## 목표

Artist 1·3에서 사용자 승인된 D1 개별 상태를 전체 pack 완료까지 기다리지 않고, 승인·해시·anchor·
승격 게이트를 충족하는 즉시 해당 gameplay 상태에 안전하게 적용한다.

## 사용자 확정 실행 조건

- 생 네기마·익는 중처럼 개별 상태가 승인될 때마다 바로 runtime 적용한다.
- 아직 승인 아트가 없는 상태는 명시적 단순 도형과 `개발 중` 라벨로 표시한다.
- 구형 아트나 가장 가까운 승인 상태를 미완성 상태의 대체물로 사용하지 않는다.
- 조립·그릴·드링크 클릭 조작에서 플레이어 신체 부위를 표시하지 않는다.

## 범위

### 포함

- 승인 상태별 runtime handoff 검증, dry-run, 일회성 영수증과 명시적 write
- manifest ID·URL·SHA·anchor·bounds·상태 ID 연결
- 정확히 일치하는 상태에만 승인 에셋을 표시하는 렌더 어댑터
- 미승인 상태 전용 개발 placeholder와 정식 manifest ID 분리
- `1920×1080`·`1280×720` 상태별 시각·입력 회귀

### 제외

- 조립·그릴 음식·shader·해당 finalizer — Artist 1 작업 000 책임
- 드링크·서빙·정리·엑스트라·정산과 해당 finalizer — Artist 3 작업 025 책임

- review 파일·원본 파일의 직접 복사 또는 manifest 수동 편집

## 작업 절차

1. Artist 1 작업 000과 Artist 3 작업 025의 승인 bundle·finalizer 결과를 동일 schema의 상태별
   인수 목록으로 만들고 `semanticOwner`가 중복된 ID를 차단한다.
2. 그릴 tray·음식 항목은 checkerboard·단독 모델 승인을 중간 증빙으로만 보고,
   `CM-GRILL-STATION-QUEUED-SELECTION R3`의 실제 위치에 합성한 FHD/720 소비 화면
   원근·톤 승인이 있는지 먼저 검증한다.
3. 각 항목을 promotion dry-run으로 검증하고 영수증 확인 뒤 원자적으로 승격한다.
4. gameplay 상태 ID와 manifest ID를 1:1 또는 명시적 합성 계약으로 연결한다.
5. 미승인 상태에는 별도 개발 placeholder component만 렌더링한다.
6. 승인 항목 추가마다 manifest·FHD/720·회귀 테스트를 실행한다.
7. 모든 D1 사용자 노출 상태가 승인 아트인지 공개 게이트에서 집계할 수 있게 한다.

  `(176,104,1278,64)`, order detail은 `(176,176,1278,72)`, help rail은

  48px 왼쪽에서 끝난다. 다섯 semantic DOM 영역과 reserved의 교차 면적은 각각 `0px²`다.

  `(1001.3333333,60.6666667,220,278.6666667)`이고, 실제 DOM은 status

- R6는 사용자 승인됐지만 finalizer handoff와 최종 소비 화면 승인이 없으므로 manifest 승격,
