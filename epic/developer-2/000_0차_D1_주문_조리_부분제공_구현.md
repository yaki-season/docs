# 개발자 2 - 000 0차 D1 주문·조리·부분 제공 구현

- 상태: `완료`
- 담당자: `개발자 2`

## 목적

`app`에서 첫 손님 `REGULAR_TSUKIOKA`의 `D1-ORDER-001`을 실제로 검증 가능한 흐름으로
구현한다. 범위는 **손님 입장 → 네기마 3개와 생맥주 1잔 주문 → 생맥주 제조·부분 제공 →
네기마 3개 조립·2칸 그릴 조리·회수 → 최종 제공·손님 반응**이다.

이 작업은 Artist 000과 병행한다. Developer 2는 게임 상태·입력·DOM UI·자동 검증·승인
아트 소비 adapter를 구현하고, Artist는 전체 장면·에셋 제작·격리 승인·소비 화면 승인·runtime
handoff를 담당한다. 어느 쪽도 상대 역할의 승인·인계 게이트를 건너뛰지 않는다.

## 정본 시나리오와 품질 계약

- 주문은 `D1-ORDER-001`: 네기마 `3`, 생맥주 `1`이다.
- 고정 가이드는 주문 접수 → 생맥주 제조 → 생맥주 부분 제공 → 네기마 세 개 조립 → 2칸 그릴에서
  앞의 두 개 조리·회수 → 남은 한 개 조리·회수 → 네기마 세 개 최종 제공 → 손님 반응이다.
- 네기마의 면별 기준은 `GPL-004` §25-1 및 §49-1을 그대로 사용한다. 양면 적정=`Perfect`,
  적정+과다=`Good`, 양면 과다 또는 적정+덜 익음=`OK`이며, 그 밖의 제공 가능/불가 판정도 같은
  조항을 따른다.
- 생맥주는 `GPL-004` §40~45, §49-2의 맥주 `3초`·거품 `1초`, 각 허용 범위와 넘침·복구 규칙을
  그대로 사용한다. 두 단계 적정=`Perfect`, 한 단계 이탈=`Good`, 두 단계 이탈=`OK`이다.
- `Perfect/Good/OK/Fail`의 판매율·만족 점수·수량 가중 주문 만족도는 `GPL-004` §47~49를
  그대로 사용한다. 이 작업에서 새 임계값, 점수, 반응 문구를 정하지 않는다.

## 구현 범위

### 포함

1. 콘텐츠에서 D1 손님·주문·항목 수량을 읽는 상태와, 손님 입장/대기/부분 제공/전체 제공 완료
   전이를 구현한다.
2. 생맥주 단일 레버의 맥주·거품 순차 입력, 완성품 공용 준비 목록 이동, D1 대상 부분 제공을
   구현한다.
3. 네기마 3개의 독립 조립 상태, 2칸 독립 면별 타이머, 대기열·회수·공용 준비 목록을 구현한다.
4. 공용 완성품을 주문에 배정할 때 메뉴·조리 방식·남은 수량을 검사하고, 부분 제공 뒤에는 해당
   항목만 완료 표시되게 구현한다.
5. 의미 텍스트, 수량 `xN`, 완료 원형 체크, 시간/진행값과 접근성 신호는 DOM/CSS로 구현한다.
   이 값들을 래스터에 굽지 않는다.
6. 기존 단일 꼬치의 방치→탄 상태→실패/재시작 회귀와 FHD 성능 실패를 재현·수정하고, 새 D1
   기능이 이를 다시 깨지지 않게 한다.

### 제외

- 인트로·D2 이후·다중 손님 러시·정산·성장·후속 메뉴·전체 화면 shell.
- 새 아트 생성, 기존 승인 아트 수정, 미승인 아트 사용, `public/assets/manifest.json` 직접 편집.
- 최종 runtime 등록. Artist가 소비 화면 재조립·최종 승인·finalizer를 끝내기 전에는 금지한다.

## 테스트 우선 절차

1. 현재 기준선의 E2E 5 실패(탄 상태 4건, FHD 성능 1건)를 이름·해상도 그대로 재현한다.
2. 순수 상태/콘텐츠 테스트로 D1 주문 생성, 입장, 수량, 부분 제공, 불변성부터 고정한다.
3. 생맥주 `Perfect`, `Good`, `OK`와 네기마 `Perfect`, `Good`, `OK`를 각각 정본 입력으로
   만들고, 품질·제공 가능 여부·공용 준비 목록·수량 가중 주문 만족도를 검증한다.
4. 네기마 3개가 2칸 그릴에서 독립 타이머로 진행되고, 앞의 두 개 회수 뒤 마지막 한 개가
   진행되는 것을 검증한다.
5. 잘못된 재료, 이른 회수, 맞지 않는 완성품 제공, 초과 제공, 취소, 빠른 이중 입력이 주문·공용
   수량·타이머를 바꾸지 않는 것을 검증한다.
6. `1920×1080`과 `1280×720`에서 입장·주문·생맥주 부분 완료·네기마 최종 완료 상태를 E2E로
   검증한다. 시각 검수 캡처는 `app/tests/reference-images/`의 기존 검증 이미지를 보존한 채
   별도 관리한다.

`npm run assets:validate`는 8개 manifest 항목을 통과했다. Developer 2는 승인 이미지의 DOM 치환
계약을 유지하고, 미승인·원본·review 파일을 runtime 경로로 제공하거나 정식 화면의 대체 asset으로
숨겨 쓰지 않는다.

## Artist와 병행할 때의 인계

- Artist → Developer 2: 사용자 승인 provenance, source revision·SHA, 주문 패널 DOM/CSS 계약,
  소비 화면 재조립 승인 뒤의 runtime handoff.
- Developer 2 → Artist: D1 화면의 실제 `screenId`/상태명, 필요한 anchor·hit area·DOM 안전 영역,
  `1920×1080`/`1280×720` 검수 해상도와 시각 회귀 요구.
- 공통: 상태 의미가 바뀌거나 새로운 UI/에셋 의미가 필요하면 구현·생성 전에 사용자에게 질문한다.
  Developer 2는 Artist의 다음 제작 항목을 임의로 정하지 않으며, Artist는 Developer 2의 상태 전이를
  임의로 단순화하지 않는다.

## 완료 기준

- [x] D1 손님 입장부터 최종 제공까지 자동 테스트가 있다.
- [x] 생맥주 부분 제공 뒤에는 생맥주만 완료이고 네기마 3개는 미제공으로 남는다.
- [x] 네기마 3개와 2칸 그릴의 독립 조리·대기열·회수가 자동 검증된다.
- [x] 네기마·생맥주 각각의 `Perfect/Good/OK`와 주문 만족도가 GPL-004와 일치한다.
- [x] 잘못된/중복/초과 입력이 상태와 수량을 훼손하지 않는다.
- [x] 기존 탄 상태·재시작 E2E 4건과 FHD 성능 E2E 1건이 통과한다.
- [x] FHD/720p E2E에서 D1 네 핵심 상태가 검증되고, 기존 app 검증 참조 이미지는 보존된다.
- [x] Artist 승인 원본을 직접 복사·등록하지 않았고, 실제 runtime 반입이 필요할 때는 promotion
  dry-run·일회성 영수증·명시적 write를 모두 통과했다.

## 구현 결과

- 기준 문서: `GPL-002 v1.10.0`, `GPL-003 v4.11.0`, `GPL-004 v1.35.0`, `UI-002 v5.24.1`,
  `ART-003 v5.0.0`, `SYS-004 v3.1.0`; 본 태스크의 착수 기준은 `v1.0.0`이다.
- 구현 위치: `app/src/state/d1/session.js`의 순수 D1 상태 머신과 `app/src/d1.html` 전용 DOM
  검증 화면이다. 공용 준비 목록·부분 제공·2칸 독립 그릴·품질/수량 가중 만족도는 렌더링과 분리했다.
- 검증: Vitest `108`개 전체 통과, D1 화면 E2E는 `1280×720`·`1920×1080` 각 1건 통과,
  기존 탄 상태·재시작 E2E는 두 해상도 총 4건 통과, FHD 성능 E2E 1건 통과.
- 회귀 수정: 면별 완전 탄 기준 `21초`와 맞지 않던 기존 E2E `15초` 대기를 `30초`으로 보정했고,
  SCN-001 렌더러의 매 프레임 resize·고밀도/보존 버퍼 비용을 제거해 FHD 성능 기준을 충족했다.
- 아트 경계: Artist가 사용자 승인 뒤 runtime handoff와 promotion을 완료했다. 구현은 이제
  manifest의 D1 승인 URL만 소비하며 원본·review 파일을 직접 참조하지 않는다.
