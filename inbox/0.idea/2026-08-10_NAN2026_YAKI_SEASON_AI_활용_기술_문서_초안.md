## 1. 요약

YAKI SEASON은 두 명의 사람과 역할별 AI 에이전트가 23일 동안 함께 만든 웹 게임이다. 우리는 AI에게 곧바로 코드를 생성하게 하기보다, AI가 무엇을 읽고 수정할 수 있는지와 어떤 판단은 사람이 해야 하는지를 먼저 문서로 정의했다.

프로젝트는 요구사항, 구현, 아트 작업을 세 저장소로 분리했다. AI는 PM, 개발자, 아티스트와 QA 등 8개 역할로 나뉘어 정해진 경로를 중심으로 작업한다. AI가 만든 코드와 그림은 자동 검증과 사람 승인을 모두 통과해야 게임에 반영된다.

### 핵심 활용 방식

- 사람의 기획 원본을 요구사항, 태스크와 테스트 조건으로 구조화
- 역할별 코딩 에이전트로 게임 로직, 데이터, 화면 통합과 회귀 테스트 개발
- 콘셉트, 캐릭터, 조리 스테이션과 음식 이미지 생성 및 반복 보정
- 에셋마다 사용 도구, 프롬프트, 후처리, 파일 지문과 승인 결과를 provenance로 기록
- 런타임 반영 전에 스키마, 해상도별 화면 재합성, 자동 테스트와 사람 승인을 결합

AI는 후보를 만들고 실행을 보조한다. 게임 방향, 충돌하는 요구사항의 선택, 저작권 확인, 아트 승인, 플레이 감각과 최종 제출 여부는 사람이 결정한다.

### 전체 작업 흐름

```text
[사람 2명]
아이디어 원본 기록 · 우선순위 결정
그림과 시나리오 승인 · 직접 플레이 판정
        │ 작업 지시
        ▼
[AI 에이전트 8개]
PM ─┬─ 개발자 1: 게임 규칙
    ├─ 개발자 2: 화면과 에셋 연결
    ├─ 개발자 3: 데이터와 검증 도구
    ├─ 아티스트 1·2·3: 이미지 자산
    └─ 통합 QA: 회귀와 공개 점검
        │ 결과물
        ▼
[자동 검증]
에셋 규격 · 기준 이미지 36장 · 단위/통합 테스트 · 브라우저 E2E
        │ 모든 게이트 통과
        ▼
[게임 반영]
```

사람 승인이나 플레이테스트 합격이 없으면 완료로 처리하지 않고 담당 역할로 되돌려 수정한다.

## 2. 사용한 AI 및 제작 도구

작업 성격에 따라 생성형 AI와 결정적 자동화 도구를 구분했다.

| 구분 | 도구/모델 | 용도 | 근거 |
|---|---|---|---|
| 주 개발 에이전트 | Claude Code | 요구사항 정리, 문서 작성, 게임 구현, 테스트와 파이프라인 스크립트 | Git 공동 저자 트레일러와 작업 기록 |
| 보조 개발 에이전트 | OpenAI Codex CLI | 이미지 생성 작업 보조, 후처리 실행, 캐릭터 콘셉트 정리 | 제작 이력의 `codex-native imagegen` 기록 |
| 내장 이미지 생성 | `imagegen` / `image_gen` | 배경, 소품, 음식, 캐릭터 상태와 모델 텍스처 생성 | provenance의 `generation.tool` |
| 외부 이미지 생성 | ChatGPT 세션 | 결과 편차가 큰 자산을 한 장씩 생성하고 사람 검수 | `handoff/asset-gen-bundle/` |
| 3D 자산화 | Three.js `GLTFExporter` 기반 고정 스크립트 | 생성 이미지를 3D 모델에 적용하고 삼각형 수와 필수 노드 검사 | 제작 이력의 inspection |
| 이미지 후처리 | `remove_chroma_key.py`, Pillow | 크로마키 제거, 여백 자르기, 크기 정규화 | 제작 이력의 `postProcess` |
| 자동 화면 캡처 | Playwright | 승인 후보를 실제 게임의 FHD/720p 화면에서 캡처 | `art-workspace/evidence/` |

> 원본 DOCX에 기재된 세부 모델명 `Opus 4.8 / Opus 4.8 1M / Opus 5`는 실제 사용 계정의 모델 선택 이력과 공식 표기를 확인한 뒤 최종 제출본에 반영한다.

### 도구를 나눈 기준

- 세 저장소를 함께 읽으며 문서, 코드와 테스트를 정합화하는 작업은 개발 에이전트가 맡았다.
- 그림 생성과 후처리를 반복하는 작업은 Codex의 이미지 생성 워크플로를 활용했다.
- 캐릭터처럼 결과 편차가 큰 자산은 한 번에 한 장만 만들고 사람이 매번 판정했다.
- 생성 이후의 배경 제거, 크기 정규화, 3D 변환과 캡처는 AI의 자유 판단을 배제하고 고정 스크립트로 처리했다. 같은 입력에서 같은 결과가 나와야 재검증할 수 있기 때문이다.

## 3. AI 실행 구조

### 3.1 저장소 분리로 AI 권한 제한

AI의 작업 범위를 말로만 설명하지 않고 파일 경로와 저장소 경계로 제한했다. 각 저장소에는 세션 시작 시 읽어야 하는 `AGENTS.md`가 있다.

```text
[1] docs/inbox/
사람이 정제하지 않고 기록한 원본 — AI는 읽되 수정하지 않음
        │ 분석·구조화
        ▼
[2] docs/spec/ + docs/epic/
무엇을 만들지와 누가 언제 만들지를 정의
        │ 구현
        ▼
[3] app/
소스, 테스트, 데이터와 승인된 런타임 에셋
        ▲
        │ 승인 파이프라인을 통과한 아트만 승격
[*] art-workspace/
생성 원본, 검수판, provenance와 반려 이력
        │
        ▼
[4] 사람 플레이테스트
불합격이면 새로운 원본 요청으로 다시 순환
```

| 저장소 | AI가 할 수 있는 일 | AI가 할 수 없는 일 |
|---|---|---|
| `docs` | 원본 읽기, 요구사항·태스크 작성과 갱신, 진행 현황 동기화 | 실행 코드 추가, 배포 자동화 추가, 사람이 작성한 원본 수정·이동·삭제 |
| `app` | 소스·테스트·데이터·빌드 설정 작성, 검증 실행 | 정제되지 않은 원본만 보고 구현 시작, 에셋 manifest를 임의 편집 |
| `art-workspace` | 자산 생성, 격리 검수, 화면 합성, 제작 이력 기록 | 등록 허용 플래그 직접 변경, 검수용 파일을 게임 폴더로 직접 복사 |

### 3.2 AI를 8개 역할로 분리

하나의 긴 AI 세션이 게임 전체를 다루면 앞선 결정을 잊거나 여러 작업이 같은 파일을 덮어쓸 위험이 있다. 이를 줄이기 위해 역할과 쓰기 범위를 분리했다.

| 역할 | 담당 | 직접 다루지 않는 영역 |
|---|---|---|
| PM | 진행 상황, 의존관계, 우선순위, 승인 요청과 다음 작업 배정 | 게임 코드와 아트 직접 제작 |
| 개발자 1 | 게임 규칙, 하루 영업 흐름, 저장과 복구 | 아트 원본, 에셋 manifest |
| 개발자 2 | 화면과 대사, 상태별 아트 연결, 승인 아트 등록 | 아티스트 원본 수정, 승인 대행 |
| 개발자 3 | 콘텐츠 데이터, 스키마, 계약 테스트와 회귀 도구 | 게임 기능과 화면의 직접 구현 |
| 아티스트 1 | 조립·그릴·음식 모델과 셰이더 | 다른 아티스트 자산과 게임 등록 |
| 아티스트 2 | 가게 외관, 소품과 인물 초상 | 조리·드링크 자산 |
| 아티스트 3 | 드링크, 서빙, 정리와 정산 화면 | 음식 셰이더 |
| 통합 QA | 결함 재현·분류·재검증, 공개 전 점검 | 기능 의미 수정, 사람 승인 대행 |

동시에 실행하는 역할은 쓰기 경로가 겹치지 않도록 배치한다.

```text
개발자 1   → app/src/domain/          게임 규칙
개발자 3   → app/content/             데이터와 스키마
아티스트 3 → art-workspace/review/    아트 제작과 검수

사람 승인 이후
개발자 2   → app/public/assets/       단일 소비자를 통한 등록
```

- 한 파일, 한 자산, 한 등록 작업은 한 시점에 하나의 역할만 쓴다.
- 원본 DOCX 기준 동시 실행 역할은 최대 3개로 운영했다.
- 에이전트의 완료 보고만 신뢰하지 않는다. PM이 실제 diff, 파일 해시와 테스트 결과를 확인하고 증거가 없으면 되돌려 보낸다.

### 3.3 기록 충돌 시 우선순위

AI의 대화 기억은 가장 낮은 우선순위에 둔다.

1. 사용자가 가장 최근 확정한 지시
2. 현재 확정된 요구사항 문서
3. 현재 담당 태스크 문서
4. 전체 작업 현황 대시보드
5. 역할별 인계 기록
6. 실제 파일과 검증 결과
7. 과거 대화 기억

실제 구현이 요구사항과 다르더라도 구현을 자동으로 정답으로 간주하지 않는다. 차이를 보고하고 PM이 처리할 때까지 의미를 임의 변경하지 않는다.

## 4. AI 파이프라인

### 4.1 사람 원본에서 구현까지

```text
1. 사람이 inbox에 정제하지 않은 원본을 기록
2. AI가 원본의 SHA-256 계산
3. 처리 이력과 대조해 신규·변경·중복 판정
4. 현상, 원하는 결과, 이유와 영향 범위를 분리
   └─ 부족하거나 모순되면 확정하지 않고 질문 필요로 보류
5. 요구사항 문서를 생성 또는 갱신하고 원본 해시 연결
6. 관련 태스크 전체의 영향 분석
   ├─ 대기: 범위와 완료 기준 갱신
   ├─ 진행 중: 변경 확인 필요로 전환하고 재작업 범위 기록
   ├─ 완료: 기존 기록을 보존하고 후속 태스크 생성
   └─ 없음: 담당 역할에 신규 태스크 생성
7. 작업 현황 대시보드 동기화
8. app에서 구현·검증하고 근거를 태스크에 기록
```

구현 중 새 문제가 발견되면 AI가 기획을 임의 수정하지 않는다. 사람이 변경 원본을 기록한 뒤 같은 파이프라인을 다시 실행한다.

### 4.2 이미지 생성과 9단계 승인

초기에는 한 화면을 통째로 생성한 뒤 배경, 인물과 도구를 잘라 쓰려 했다. 하지만 잘린 경계와 원근 불일치 때문에 재작업이 반복되었다. 이후 `프롬프트 1개 = 자산 1개` 원칙으로 전환하고, 각 자산을 체커보드 위에서 독립 검수했다. 사용을 중단한 화면 단위 프롬프트도 삭제하지 않고 폐기 근거로 보존했다.

| 단계 | 처리 | 판단 주체 |
|---:|---|---|
| 1 | 단일 자산을 단색 크로마키 배경으로 생성 | AI 보조 |
| 2 | 배경 제거, 여백 자르기, 크기 정규화 | 고정 스크립트 |
| 3 | 체커보드 위 격리 검수판 생성 | 고정 스크립트 |
| 4 | 개별 자산 승인 | **사람** |
| 5 | 실제 게임 화면에서 1920×1080·1280×720 재합성 | 자동화 |
| 6 | 용량과 해상도 최적화 | 고정 스크립트 |
| 7 | 소비 화면 상태의 최종 승인 | **사람** |
| 8 | 원자적 런타임 등록; 일부 실패 시 전체 복구 | 자동화 |
| 9 | 기존 기능 회귀 테스트 | 자동화+사람 |

#### Provenance 기반 역추적

```text
게임의 런타임 에셋
        ▲ 등록 기록
런타임 인계 파일
        ▲ 9단계 통과 시 생성
provenance.json
        ▲ 도구 · 프롬프트 · 후처리 · 승인 · SHA-256
사람이 승인한 원본
        ▲
자체 아트 기준 YS-HANDCRAFTED-NIGHT-v1
```

에셋별 제작 이력에는 다음을 기록한다.

- 에셋 ID와 상태
- 사람 승인 날짜와 승인 근거
- 참조 원본 경로와 SHA-256
- 생성 도구와 프롬프트 요약
- 크로마키 제거·크롭·크기 정규화 등 후처리
- 최종 파일의 형식·크기·SHA-256
- GLB의 경우 삼각형 수와 예산
- 포함하면 안 되는 요소 목록
- 다음 승인 질문과 다음 게이트

`runtimeRegistrationAllowed`의 기본값은 `false`다. 사람이나 AI가 직접 이 값을 바꾸는 대신, 모든 게이트를 통과한 finalizer만 런타임 인계 파일을 만들 수 있다.

### 4.3 자동 검증

```text
npm run verify
  1. 런타임 에셋 파일과 manifest·스키마 검증
  2. 기준 이미지 36장의 SHA-256과 viewport 검증
  3. Vitest 단위·통합 테스트
  4. Chromium FHD/720p E2E 테스트
        ▼
  사람이 직접 플레이해 합격해야 완료
```

원본 DOCX에는 한 시점의 게임 규칙 테스트 400개가 기록되어 있다. 테스트 수는 개발 과정에서 변하므로 제출 빌드의 `npm run verify` 결과, 실행 시각과 커밋 SHA를 최종 문서에 기재한다. 사람은 최소한 프롤로그, 첫 손님과 하루 전체 영업을 직접 확인한다.

## 5. 재사용 가능한 프롬프트 자산

프롬프트를 일회성 채팅으로만 두지 않고 저장소 파일로 관리한다.

- 역할 시작 프롬프트 8종
- PM이 사용하는 작업 지시 템플릿
- 모든 이미지에 적용하는 공통 스타일 프롬프트
- 자산별 대상·유지·금지·배경 프롬프트

### 5.1 역할 시작 프롬프트의 구성

역할 프롬프트에는 다음 항목을 포함한다.

- 역할과 책임, 직접 하지 않는 일
- 세 저장소와 `AGENTS.md`를 찾는 부팅 절차
- 현재 브랜치, HEAD, dirty 파일과 실행 프로세스 점검
- 대시보드 상태와 실제 태스크 수 재집계
- handoff의 diff·artifact SHA·테스트 대조
- 사용자 승인 큐, 외부 입력 대기와 문서 drift 분리
- 첫 변경 전 진행표·임계 경로·승인 큐 보고

### 5.2 작업 지시 템플릿

```text
runId:                       우선순위: P0 | P1 | P2 | P3
역할/persona:                왜 지금 필요한가:
stage:                       막고 있는 gate:
epic/버전:                   목표:
허용 쓰기 경로:
읽기 전용 입력과 SHA:
선행 조건:
포함:
제외:
완료 기준과 테스트:
사용자 승인 / 사람 화면 gate:
생산자 → 소비자:
완료 후 다음 작업:
보고 형식: 변경 파일, artifact/SHA, 테스트 명령·결과, blocker, handoff 경로
```

무엇을 만들지뿐 아니라 허용 경로, 제외 범위와 완료 증거를 함께 전달한다.

### 5.3 공통 아트 프롬프트

특정 작가 이름을 모방하지 않고 `YS-HANDCRAFTED-NIGHT-v1`이라는 자체 시각 기준을 사용한다.

```text
Style/medium: YS-HANDCRAFTED-NIGHT-v1 original hand-drawn 2.5D game illustration.
Visible pencil underdrawing, slightly irregular ink, opaque gouache blocks,
paper grain, worn wood/brass/ceramic, deliberate shape-explaining pixel clusters.
No glossy 3D.

Lighting/mood: warm amber task light and lanterns against deep but readable indigo night.
Color palette: amber, burnt orange, deep indigo/navy, dark walnut, cream paper, aged brass.

Constraints: no generated semantic text or numbers, no fake Japanese,
no watermark, no border, no captions.

Avoid: photorealism, glossy PBR, uniform vector lines, full-screen orange tint,
crushed blacks, random pixel noise, impossible perspective.
```

문구와 수치는 이미지가 아닌 HTML UI로 표시한다. 값이 바뀌어도 그림을 다시 만들지 않고 접근성과 테스트 가능성을 유지하기 위해서다.

### 5.4 자산별 프롬프트 예시

```text
[대상] exactly one coherent bite-sized raw chicken-thigh piece
[유지] retain source palette, marbling, cream-fat highlights, dark pixel contour
[금지] no skewers, other food, UI, scene, or shadow
[배경] uniform #00ff00 chroma-key background
```

반려 사유는 다음 리비전의 금지 조건으로 편입한다. 예를 들어 손님 화면의 입구를 벽이나 두 번째 카운터로 바꾸는 오류가 반복되면 이를 명시적 금지 계약으로 추가한다.

## 6. AI 통제 장치

### 6.1 금지한 행위

| 금지 행위 | 방지하려는 사고 |
|---|---|
| 과거 대화 기억만으로 작업 재개 | 사라진 맥락을 AI가 지어내는 문제 |
| 사람이 쓴 원본 수정·이동·삭제 | 정리 과정에서 원래 요청이 훼손되는 문제 |
| 원본 메모를 검토 없이 요구사항으로 확정 | 검증되지 않은 착상이 구현으로 직행하는 문제 |
| 요구사항·자산 번호 추측 | 존재하지 않는 계약을 만들어내는 문제 |
| `git reset`, `checkout`, `clean`으로 작업물 제거 | 다른 사람이나 세션의 작업 유실 |
| 다른 역할이 수정 중인 파일 덮어쓰기 | 병렬 작업 충돌과 결과 유실 |
| manifest 또는 등록 허용 플래그 직접 변경 | 승인되지 않은 아트의 런타임 유입 |
| 검증하지 않은 상태를 완료로 기록 | 낙관적인 허위 완료 보고 |
| 승인 대기 중 다음 후보 무한 생성 | 비용 증가와 승인 큐 혼선 |

### 6.2 사람만 내리는 결정

| AI가 수행 | 사람이 수행 |
|---|---|
| 요구사항 구조화와 문서 초안 | 그림과 시나리오 최종 승인 |
| 코드·테스트 작성과 실행 | 직접 플레이 후 합격 판정 |
| 이미지 생성과 검수판 준비 | 충돌하는 요구사항의 우선순위 결정 |
| 진행 상황 기록과 동기화 | 원격 저장소 업로드와 외부 제출 결정 |

AI는 사람 전용 판단을 대신하거나 승인받았다고 임의 기록할 수 없다.

### 6.3 실패와 충돌 처리

- 테스트가 간헐적으로 실패하면 첫 실패와 재시도 결과를 모두 기록한다.
- 테스트 결과에는 실행 커밋과 dirty 상태를 함께 남긴다. 이후 코드가 바뀌면 이전 결과를 현재의 통과 근거로 사용하지 않는다.
- 사람이 반려한 그림에는 재제출 금지 상태를 기록해 같은 결과나 파생본이 다시 올라오지 않게 한다.
- 일부 에셋 등록이 실패하면 파일과 manifest 변경을 모두 원래 상태로 복구한다.

## 8. 기술적 의의와 배운 점

이 프로젝트에서 AI 활용의 핵심은 생성량이 아니라 통제 가능한 협업 구조였다.

1. **AI의 기억 대신 저장소를 기억 장치로 사용했다.** 프롬프트, 결정, 요구사항, 테스트와 승인 근거를 파일로 남겨 세션이 바뀌어도 복구할 수 있게 했다.
2. **생성과 승인을 분리했다.** AI가 만든 후보가 곧 게임 자산이 되지 않으며, 사람 승인과 실제 소비 화면 검수를 통과해야 한다.
3. **자유 생성 이후는 결정적으로 처리했다.** 배경 제거, 정규화, 3D 변환, 캡처와 등록은 재현 가능한 스크립트가 맡는다.
4. **완료를 증거로 정의했다.** 에이전트의 보고가 아니라 diff, SHA-256, 자동 테스트와 사람 플레이 결과가 완료를 결정한다.
5. **실패도 자산으로 남겼다.** 폐기 프롬프트, 반려 사유와 충돌 기록을 보존해 같은 실패를 반복하지 않게 했다.

결과적으로 두 명의 팀이 기획, 코드, 데이터, 이미지 자산과 QA를 병렬로 진행하면서도 각 결과물의 출처와 승인 상태를 추적할 수 있었다. YAKI SEASON의 AI 활용은 “AI가 게임을 대신 만들었다”가 아니라, 사람이 방향과 품질을 책임지는 가운데 AI가 역할별 제작 속도와 탐색 범위를 확장하도록 설계한 사례다.
