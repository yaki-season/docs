# 게임 소개(200자)

《YAKI SEASON》은 비 내리는 밤, 야키토리 가게를 이어받은 주인공 아키의 하루를 그린 픽셀 아트 경영 어드벤처입니다. 아키는 손님 주문을 받고 꼬치를 굽고 생맥주를 따라 내며 가게를 운영합니다. 단골 츠키오카를 비롯한 다양한 손님과 대화하고, 메뉴·장비를 업그레이드하며, 하루의 결과에 따라 가게와 인물들의 이야기를 이어갑니다.

# Codex와 함께 게임을 만든 과정 (500자 내외)

Codex는 기획을 구현 가능한 작업으로 나누고, 프로젝트 구조와 규칙을 확인하면서 개발을 보조했습니다. 주요 활용 영역은 손님 상태 흐름과 좌석 매핑, 주문·꼬치·생맥주 상호작용, UI 및 반응형 화면 정리, 아트 에셋 규격 검증, 캐릭터 이미지의 투명 배경·해상도 통일, LoRA 데이터셋 manifest 작성과 학습 실행 기록 관리였습니다. 또한 파일 경로와 인게임 슬롯을 연결하고, 누락된 상태 이미지와 잘못된 배경이 섞인 문제를 점검해 수정 후보를 분리했습니다. 이미지 생성에서는 공통 화풍을 맞추기 위해 실제 인게임 레퍼런스를 선별하고, 베이스 모델과 LoRA 설정을 바꿔가며 학습·검증했습니다. Codex가 담당한 부분은 코드 작성·수정, 스크립트와 설정 파일 생성, 검증 명령 실행, 결과 정리와 문서화입니다. 게임의 핵심 아이디어, 캐릭터·메뉴·연출에 대한 최종 판단, 원하는 이미지의 승인과 수정 방향 결정, 실제 결과 검수는 제가 직접 진행했습니다. 생성 결과가 요구사항과 다를 때는 Codex의 결과를 그대로 채택하지 않고 사람이 확인한 뒤 다음 작업을 결정했습니다.

# 01. Codex를 어디에 사용했나요?

- 인게임 구현 및 검증

손님 상태 흐름과 좌석 매핑, 주문과 꼬치 조리, 생맥주 상호작용 같은 게임 로직을 Codex와 함께 구현했습니다. 구현만 맡긴 것이 아니라 검증까지 함께 걸었습니다. 유닛 테스트와 Playwright 기반 E2E 테스트를 붙여서, 기능을 고칠 때마다 실제 게임을 띄워 의도한 대로 동작하는지 자동으로 확인하도록 했습니다.

- 아트 생성 및 검수

이미지 생성부터 게임에 실제로 들어가기까지의 절차 전체에 사용했습니다. 이미지를 한 장 잘 뽑는 것보다, 뽑은 이미지가 다른 자산과 같은 화풍과 규격으로 맞는지 검수하고 런타임에 등록하는 절차가 훨씬 큰 문제였기 때문입니다. 아트를 생성하고 격리 검수를 거쳐 규격을 정규화한 뒤 런타임에 등록하는 3단계 승인 게이트를 만들었고, 여기에 LoRA 학습 환경을 붙였습니다.


# 02. 어떤 기능을 구현했나요?

- 이미지 생성 파이프라인

생성 규약을 한 프롬프트당 자산 하나, 상태 하나로 고정했습니다. 검수할 때는 체커보드 위에 자산 하나만 올려 배경 잔재나 잘린 부분을 확인합니다. 여기에 런타임 자산 계약을 붙여서, 매니페스트에 안정 ID와 소스 리비전, SHA-256 해시, 해상도를 기록하고 자산을 교체하려면 반드시 리비전을 올려야 통과하도록 했습니다. 실제 이미지 처리로는 흰 배경에서 딴 캐릭터의 누끼를 정리하는 도구와, 1920×1080 캔버스에 인물 높이와 바닥 앵커, 중심축을 통일하는 규격 정규화 도구를 만들었습니다. 마지막으로 배경과 좌석, 카운터 레이어 위에 손님들을 실제 게임 좌표로 올려 크기와 시선 높이를 나란히 비교하는 인게임 합성 검수 페이지를 붙였습니다.

- LoRA 학습과 화풍 고정

Codex로 생성해 사람이 승인한 이미지를 학습 데이터로 삼아 화풍을 고정하는 것이 목표였습니다. 공개 가중치 모델에 PEFT 어댑터를 붙여 로컬 RTX 4060 Ti 8GB 환경에서 돌아가는 학습 파이프라인을 만들었습니다. 학습 전에 승인 플래그와 파일 존재 여부, 이미지 유효성, 캡션 형식을 검사하는 사전 검사 도구를 두었고, 같은 시드로 베이스 모델과 LoRA 결과를 나란히 생성해 효과를 판별하는 비교 생성 스크립트를 붙였습니다. 데이터셋 해시와 LoRA 해시, 스텝 수, rank, 승인 여부를 기록하는 실행 레지스트리로 어떤 데이터로 무엇을 학습해 어떤 결과가 나왔는지 추적했습니다. Stable Diffusion 1.5에서 시작해 AnythingV5와 DreamShaper-8을 거쳐 Illustrious-XL과 픽셀 아트 스타일 어댑터 조합까지 옮겨가며 19종의 설정으로 20회를 학습했고, 화풍을 배우는 LoRA와 특정 캐릭터의 동일성을 배우는 LoRA는 데이터셋을 분리했습니다.

- Spec Driven Development

코드를 먼저 짜지 않고 명세를 먼저 확정하는 방식으로 진행했습니다. 제가 아이디어나 수정 요청을 원본 그대로 넣어두면 Codex가 그것을 분석해 아트, 게임플레이, 시나리오, UI, 데이터, 시스템, QA 등 영역별 명세로 정제하고, 그 명세를 근거로 역할별 작업 문서를 만든 뒤, 그 작업 문서를 보고 구현하는 흐름입니다. 현재 명세 38건과 작업 문서 53건이 이렇게 쌓였습니다.

이 방식이 실제로 힘을 발휘한 부분은 추적입니다. 명세와 작업 문서에는 전부 버전을 붙였고, 원본은 SHA-256 지문으로 식별해 같은 내용이 두 번 반영되지 않도록 했습니다. 완성된 런타임 자산에도 근거가 된 명세의 번호와 버전을 함께 기록해두었기 때문에, 게임 안의 이미지 한 장에서 그것을 만들라고 지시한 명세와 그 명세를 낳은 제 원본 메모까지 거슬러 올라갈 수 있습니다.

이미지 쪽은 게임용 이미지 생성 및 규격화 계약이라는 문서에 화면 기준, 공통 스타일 프로파일, 보이는 픽셀 밀도, 좌석 인물의 캔버스와 앵커, 스토리 장면 구도, 꼬치 이미지 조립 단계까지 종류별로 정량으로 명시해두었습니다. Codex는 매번 이 명세를 읽고 작업했기 때문에 세션이 바뀌거나 대화가 끊겨도 같은 기준으로 결과가 나왔습니다. 화풍이 흔들리지 않은 이유는 프롬프트를 잘 써서가 아니라 기준이 문서로 고정돼 있었기 때문입니다.


# 03. 어떤 문제를 해결했나요?

- LoRA 학습 데이터 생성

단순히 Codex로 이미지를 생성하면 화풍이 불일치하는 문제가 발생했습니다. LoRA를 튜닝하는 과정에서 Codex로 생성한 여러 이미지들을 레퍼런스로 사용하여 학습시킬 수 있었습니다. 캐릭터와 배경, 컷신, 요리 등 종류에 따라 어떻게 생성해야 하는지 화풍과 해상도를 명세한 지침서를 통해서 Codex에서 이미지를 빠르고 정확하게 생성할 수 있었습니다. 지침서를 정확히 따라주었기 때문에 Codex를 통해 생성한 많은 이미지들을 실제 인게임 리소스로 사용할 수 있었습니다.

학습 데이터가 오염되는 문제도 있었습니다. 작업공간 이미지를 그대로 넣었더니 UI 스크린샷과 게임플레이 배경이 섞여 들어가 결과물에 UI 잔상이 나왔습니다. 승인된 컷신 10장과 스타일 레퍼런스 1장만으로 정제한 데이터셋을 따로 만들어 다시 학습했습니다. 과적합 지점을 고르는 것도 문제였는데, 체크포인트를 50, 100, 150, 200 스텝으로 모두 뽑아 비교해보니 후반 체크포인트는 같은 인물과 목조 건물 구조를 반복해서 그렸습니다. 50 스텝을 검토 후보로 채택하고 나머지는 버렸습니다.

- Playwright 기반 인게임 human 게이트

이미지가 규격에 맞는지는 파일만 봐서는 알 수 없고, 실제 게임 화면에 올려봐야 드러납니다. 그래서 Playwright로 실제 게임을 띄워 의미 있는 상태마다 화면을 캡처하고 해시를 기록하는 검수 하네스를 만들었습니다. 사람은 이 캡처 묶음만 보고 승인 여부를 판단하면 되고, 승인된 캡처는 기준 이미지로 고정되어 이후 회귀 검사에 쓰입니다. 기계가 증거를 만들고 사람이 판단하는 구조입니다.

실제로 이 게이트에서 잡힌 문제가 있습니다. 흰 배경에서 딴 캐릭터에 밝은 회색 1픽셀 링이 남아 있었는데, 밝은 배경에서는 보이지 않다가 어두운 밤 배경 위에 올리자 흰 테두리로 떠올랐습니다. 파일 단위 검증은 전부 통과한 자산이었습니다. 안쪽 이웃보다 밝은 경계 픽셀만 골라 지우는 방식으로 고쳐서, 생맥주 거품처럼 원래 흰 부분은 남기고 배경 잔재만 제거했습니다. 캐릭터마다 크기와 앵커가 달라 좌석에 앉은 손님들의 시선 높이가 안 맞는 문제도 같은 방식으로 발견해서, 인물 높이 690픽셀에 바닥 Y좌표 905, 중심 X좌표 960으로 기준을 통일했습니다.


# 04. 사람이 직접 결정한 부분은 무엇인가요?

무엇을 만들 것인가는 전부 사람에게서 출발했습니다. 저장소에 인박스라는 폴더를 두고 게임 아이디어와 기획서, 화면 변경 요청, 캐릭터 콘셉트, 버그와 모순 같은 것을 제가 손댄 그대로 넣었습니다. AI는 이 폴더의 원본을 수정하거나 옮기거나 지우지 못하도록 규칙으로 막아두었습니다. 모든 명세는 이 원본을 분석해서 나왔기 때문에, 게임의 어떤 부분을 따라 올라가도 결국 제가 넣은 원본에 닿습니다. 비 오는 밤의 야키토리 가게라는 설정, 아키와 츠키오카의 성격, 메뉴 구성과 하루의 흐름, 연출 톤은 전부 여기서 시작했습니다.

중간 과정에서도 결정은 사람이 했습니다. 아트 레퍼런스는 한 장씩 확인받았습니다. 자산 하나만 체커보드 위에 격리해서 보여주고, 이게 맞는 화풍인지 맞는 규격인지를 제가 판단한 다음에야 다음 단계로 넘어갔습니다. 학습에 넣을 이미지도 마찬가지입니다. 파이프라인에 작업공간의 이미지를 자동으로 전부 학습하지 않는다는 원칙을 명시했고, 제가 승인 표시를 붙인 이미지만 학습 데이터에 들어가도록 했습니다. 어떤 이미지가 우리 화풍의 정답인지는 자동으로 판별할 수 없다고 봤기 때문입니다. 체크포인트 50 스텝을 고른 것도, 그보다 뒤가 과적합이라고 판단한 것도 눈으로 비교한 결과이고, LoRA 결과는 아직 프로덕션 승인을 받지 못한 상태로 레지스트리에 미승인으로 남겨두고 있습니다.

마지막 결과도 사람이 봅니다. Playwright가 실제 게임을 띄워 상태별로 캡처를 만들어주면, 그 캡처를 보고 통과 여부를 제가 결정합니다. 인게임 합성 검수를 보다가 특정 손님이 너무 커 보인다고 판단해 10퍼센트 작게 하되 위치는 그대로 두라고 지시한 것도 이 단계에서 나왔고, 크기를 줄이면서 머리 높이를 유지하는 앵커 선택은 그 지시를 구현한 결과입니다. 자산이 게임에 들어가려면 개별 검수 승인과 소비 화면 맥락 최종 승인 두 단계를 사람이 통과시켜야 하고, Codex가 이 플래그를 직접 켜지 못하도록 파이프라인 규칙에 못 박았습니다.

정리하면 초기 아이디어와 중간 과정, 최종 QA라는 세 지점 모두에서 중요한 결정은 사람이 내렸습니다. Codex가 담당한 것은 코드 작성과 수정, 스크립트와 설정 파일 생성, 검증 명령 실행, 결과 정리와 문서화입니다. 생성 결과가 요구사항과 다를 때는 그대로 채택하지 않고 사람이 확인한 뒤 다음 작업을 결정했습니다. 이렇게 매 순간 사람이 판단을 끼워 넣었기 때문에, 아트도 게임 구현도 저희가 원한 방향에서 벗어나지 않았습니다.


# 개발 기간 구분

이 프로젝트는 해커톤 개시(2026-08-04) 이전부터 개발 중이던 YAKI SEASON을 기반으로 합니다.

기존 개발분: Three.js 기반 2.5D 렌더링과 고정 카메라 씬 구성, 첫 손님에게 네기마 한 꼬치를 조립·굽기·서빙하는 D1 코어 루프, 런타임 자산 매니페스트와 SHA-256 검증 도구를 포함한 3단계 아트 승인 게이트, Playwright 인게임 캡처 검수 하네스와 유닛·E2E 회귀 기반, 명세 36건과 작업 문서 48건 규모의 Spec-driven 문서 체계.

챌린지 기간(08-04~08-30) 신규 개발분: 하루짜리 프로토타입이던 게임을 D2 모모, D3 토치 마무리, D4 드링크·샐러드, D5 토리카와까지 실제 플레이 가능한 영업일로 확장하고 손님 구성 랜덤화·입장 정책·정산 흐름을 구현. ## (참고) 상세 근거


프로젝트 자체는 2026년 7월 19일에 시작했습니다. 챌린지 시작 시점인 8월 4일까지 만들어져 있던 것은 첫 손님 츠키오카에게 네기마 한 꼬치를 조립하고 구워 서빙하는 D1 수직 슬라이스 하나였습니다. D2와 D3는 정의 문서와 시나리오 골격만 있었고 실제로 플레이할 수 없었습니다. 챌린지 기간 동안 app 저장소에 91건을 커밋해 400개 파일에서 16,920줄을 추가하고 2,484줄을 덜어냈습니다. 같은 기간 docs 저장소에 28건, 아트 작업공간에 12건을 커밋했습니다.

- 영업일 확장: D2부터 D5까지

기간 중 가장 큰 축은 하루짜리 프로토타입이던 게임을 실제 캠페인으로 늘린 일입니다. 8월 10일에 D2 모모 영업일을 완성했고, 이어서 D3에 토치 마무리 조리와 후일담을 붙여 캠페인 흐름으로 연결했습니다. 8월 26일에는 D4 영업일과 D5 토리카와 영업일을 추가했습니다. D4는 64개 파일에서 3,082줄, D5는 63개 파일에서 1,065줄 규모의 신규 구현입니다. 여기에 손님 구성을 매 판 다르게 뽑는 로직, 조기 입장과 도착 간격 정책, 좌석 확장과 정산 흐름을 함께 붙였습니다. 검증도 같이 늘어서 E2E 테스트는 36개에서 52개로, 유닛 테스트는 49개에서 65개로 증가했습니다.

- 아트 LoRA 학습 파이프라인 신설

LoRA 관련 작업은 전부 챌린지 기간에 새로 만든 것입니다. 8월 22일에 아트 작업공간에 PEFT 기반 스타일 학습 파이프라인을 처음 추가했고, 8월 24일에는 아트 생성과 레퍼런스 관리를 전담하는 별도 저장소를 새로 만들었습니다. 이 저장소는 현재 108개 파일 규모로, 데이터셋 manifest와 승인 레퍼런스, 학습 설정, 실행 레지스트리를 담고 있습니다. 기간 중 19종의 설정으로 20회를 학습하면서 Stable Diffusion 1.5부터 Illustrious-XL과 픽셀 아트 스타일 어댑터 조합까지 베이스 모델을 옮겨가며 비교했습니다. 8월 23일에는 이 과정에서 얻은 기준을 게임용 이미지 생성 및 규격화 계약이라는 명세로 확정했습니다.

- 그 밖에 기간 중 새로 만든 것

오디오는 8월 4일 기준으로 저장소에 한 파일도 없었습니다. 기간 중 BGM과 환경음, 조리와 서빙 효과음을 포함한 83개 자산의 카탈로그와 재생 엔진을 새로 붙였습니다. 배포도 새로 붙였습니다. 8월 11일에 Vercel 호스팅과 Docker 패키징을 구성해 공개 URL로 플레이할 수 있게 만들었습니다. 조리 연출에서는 승인된 원본 한 장을 GLSL 셰이더가 굽는 방식으로 바꾸고 그릴 연기 VFX와 생맥주 셰이더를 추가했습니다. 아트 쪽은 손님 캐릭터를 전면 교체했고, 런타임 매니페스트에 등록된 자산은 35건에서 101건으로 늘었습니다.
