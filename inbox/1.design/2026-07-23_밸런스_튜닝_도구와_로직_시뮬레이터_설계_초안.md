# 밸런스 튜닝 도구와 로직 시뮬레이터 설계 초안

> 문서 상태: 초안 v0.1 · 작성일 2026-07-23 · 대상: 개발·기획용 내부 도구
>
> 근거: `inbox/0.idea/YAKI SEASON 게임 기획서.md`(수치 튜닝 필요), 기존 `app/tools/grill-tool.html`(도구 선례)
>
> 성격: 기획자가 코드 수정 없이 게임 수치를 조절하고 결과를 빠르게 확인하는 내부 도구의 기획안이다.
> `spec/` 21종 어디에도 개발·기획용 도구를 다루는 문서가 없어 이 공백을 채운다. 확정 원본이 아니라
> spec을 만들기 위한 구체화 단계다.

---

## 1. 목적

기획자가 **꼬치 조리 시간, 손님 인내심, 팁 배율** 같은 수치를 한 곳에서 조절하고, 그 변화가
게임에 어떤 영향을 주는지 **렌더링 없이 빠르게** 확인할 수 있게 한다. 지금은 수치가 코드 상수로
흩어져 있어 기획자가 직접 조절할 수 없고, 한 번 바꾸면 실제 플레이로만 확인할 수 있다.

이 도구는 두 기능을 가진다.

- **A. 밸런스 데이터 편집 UI** — 데이터 파일의 수치를 슬라이더·입력으로 조절하고 저장한다.
- **B. 로직 시뮬레이터** — 조절한 수치로 영업 루프를 빠르게 돌려 결과 지표를 보여 준다.

셰이더 부하를 UI로 확인하는 `app/tools/grill-tool.html`의 밸런스 판이다.

---

## 2. 배경과 경계

- **데이터 계약은 `DAT-001`이 이미 정의한다.** 메뉴·공정·품질·손님·영업일 데이터 단위와
  `candidate`(예시 수치) / `approved`(출시 기준) 상태 구분까지 있다. 이 도구는 그 데이터를
  **편집하고 시험하는 표면**이지, 데이터 스키마를 새로 정의하지 않는다.
- **게임 로직은 `GPL-002`(영업일 루프)·`GPL-003`(손님·주문)이 정의한다.** 시뮬레이터는 그 로직을
  **그대로 재사용**하며 별도 로직을 만들지 않는다. 렌더링만 뺀 같은 상태 함수를 돌린다.
- **도구는 출시 빌드에 포함하지 않는다.** 개발·기획 전용이다.

---

## 3. 범위

### 포함

- 데이터 파일(JSON)을 읽어 수치를 슬라이더·입력으로 조절하는 UI
- 조절한 값의 저장·내보내기와 원본 되돌리기
- `candidate` 수치를 다루고, 확정 시 `approved`로 승격하는 표시
- 렌더링 없이 한 영업일 루프를 빠르게 돌리는 시뮬레이터
- 시뮬레이션 결과 지표(매출·팁·실패율·평균 대기·품질 분포 등) 표시
- 같은 수치로 여러 번 돌려 결과가 재현되는지 확인(무작위 요소의 시드 고정)

### 제외

- 최종 밸런스 수치 자체의 결정 (도구는 조절 수단이고 값은 기획자가 정한다)
- 출시 빌드 포함과 라이브 운영용 원격 튜닝
- 에셋·아트·시나리오 편집
- 3D 장면 렌더링 (시뮬레이터는 순수 로직만)

---

## 4. 기능 A — 밸런스 데이터 편집 UI

1. 데이터 파일을 불러와 수치를 항목별로 표시한다. 예: 꼬치 면별 조리 구간, 손님 인내심 시간,
   유형별 팁 배율, 손님 생성 간격.
2. 각 수치는 슬라이더 또는 숫자 입력으로 조절하며, 조절 즉시 화면 값에 반영된다.
3. 수치에는 허용 범위와 단위(초·비율·정수)를 표시하고 범위를 벗어난 입력을 막는다 (`DAT-001` 검증 규칙).
4. 원본 대비 바뀐 항목을 강조하고, 항목·전체 되돌리기를 제공한다.
5. 조절 결과를 데이터 파일로 저장·내보낸다.
6. 각 항목의 `candidate`/`approved` 상태를 표시하고, 미확정 값이 확정값으로 혼동되지 않게 한다.

## 5. 기능 B — 로직 시뮬레이터

1. 현재 편집 중인 수치로 한 영업일 루프를 처음부터 끝까지 실행한다 (영업 시작→손님 도착→주문→
   조리→서빙→퇴장 반복→영업 종료). **렌더링과 실제 대기 없이** 모의 시간으로 빠르게 돌린다.
2. 조리·서빙은 자동 플레이어 정책(예: 항상 적정에 서빙)으로 대체하거나, 성공률을 파라미터로 준다.
   실제 사람 입력을 요구하지 않는다.
3. 결과 지표를 표로 보여 준다: 총매출·팁·실패 주문 수·손님 이탈 수·평균 대기 시간·품질 분포.
4. 같은 수치와 같은 시드는 같은 결과를 낸다 (재현성).
5. 수치를 바꾸고 다시 돌려 **직전 결과와 비교**할 수 있다.

## 6. 데이터 파일 형식 — JSON 권장

CSV와 JSON 중 **JSON을 권장한다.**

- `DAT-001`의 데이터는 **중첩 구조**다: 메뉴 → 공정 순서 → 판정 구간 → 가중치. CSV는 평면이라
  이 중첩을 표현하지 못하고 여러 파일로 쪼개야 한다.
- `DAT-001`은 레코드마다 **스키마 버전·상태(candidate/approved)·활성 여부·변경 이력**을 요구한다.
  JSON은 이걸 타입 있는 필드로 담지만 CSV는 문자열로 뭉갠다.
- 기획자가 스프레드시트로 편집하고 싶은 요구는 **이 도구의 편집 UI가 대신 해결한다**. 즉 사람은
  JSON을 손으로 고치지 않고 슬라이더로 조절하며, 파일 형식은 기계가 다루기 좋은 JSON을 쓴다.

> 정리: **저장 형식은 JSON, 편집 표면은 이 도구의 UI.** CSV가 꼭 필요한 항목(예: 대량 표 형태의
> 단순 수치)이 나오면 그 항목만 CSV 보조 내보내기를 추가할 수 있다.

## 7. 아키텍처 원칙

1. **순수 로직 공유.** 시뮬레이터는 게임과 같은 상태 함수를 쓴다. 게임·시뮬레이터·자동 테스트가
   하나의 로직을 공유하면 "시뮬레이터에서는 되는데 게임에서는 다른" 괴리가 생기지 않는다.
2. **수치는 데이터에서 온다.** 로직 코드에 조리 시간·인내심 같은 수치를 상수로 박지 않고 데이터
   파일에서 읽는다. 이래야 도구로 조절한 값이 게임에 그대로 반영된다.
3. **도구는 런타임과 분리한다.** `app/tools/` 아래 두고 출시 빌드에 포함하지 않는다.
4. **미확정 값이 확정으로 새지 않게 한다.** `candidate`는 도구에서만 시험하고, `approved`만 게임
   기본값으로 로드한다 (`DAT-001 §8`).
