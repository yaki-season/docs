## 1. 목적

손님을 화면 장식(스프라이트 + mood 문자열)이 아니라 **자율 상태 머신을 가진 도메인 엔티티**로
도입한다. 아울러 손님이 무엇을 어떤 순서로 주문하는지를 **메뉴 카테고리**로 정의해, 손님 유형 간
차이를 대부분 데이터로 표현한다.

### 이번 설계의 전제 결정

- **손님은 한 번에 1명씩** 입장한다. 멀티 손님·좌석 관리는 다음 단계.
- **인내심 게이지는 골격만.** 상태와 게이지 UI는 두되 지금은 감소시키지 않는다(무한 인내).
  멀티 손님 도입 시 플래그로 켠다.
- **품질·만족도·팁·리뷰 판정은 손님이 소유**한다. 요리사(조리 시스템)는 날것 결과만 넘긴다.

## 2. 설계 원칙

### 2.1 요리사와 손님 완전 분리

| | 요리사(Chef) | 손님(Customer) |
|---|---|---|
| 구동 | 플레이어 입력(클릭) | 자율 · 시간 |
| 표현 | 조리 상태 리듀서(함수형) | 상태 패턴(OOP 엔티티) |
| 결정 주체 | 사람 | 게임 |

- 공유 base 클래스(`Person` 등)를 만들지 않는다. 공유할 행동이 없다.
- 두 시스템이 닿는 지점은 **서빙 하나**뿐이다. 요리사가 만든 접시가 손님으로 넘어가는 순간.
- 조리 상태는 함수형 리듀서를 유지하고, 손님만 OOP 엔티티로 둔다.

### 2.2 유형 차이는 데이터로, 파생은 최소로

- **주문 순서·인내심·팁 배율처럼 값만 다르면 데이터(config)** 로 둔다.
- **판정 규칙이 다르거나(판정 override) 상태를 새로 추가할 때만** 서브클래스로 파생한다.
- 뒤(7장)에서 보듯 이 원칙과 주문 모델 덕에 서브클래스가 크게 줄어든다.

## 3. 메뉴 카테고리 (참조)

메뉴 카테고리 정의·스테이션 매핑·중복 주문 규칙은 짝 문서
`1.design/2026-07-22_메뉴_카테고리와_주문_규칙_설계_초안.md`에 있다. 본 문서는 이를 참조한다.

요약:

- 카테고리 = `음료 · 꼬치 · 튀김 · 사시미 · 사이드` (스테이션과 1:1).
- **중복 주문**: 주력(음료·꼬치) 가능 / 특선·사이드(튀김·사시미·사이드) 1회.
- 현재 실제 구현 스테이션은 `꼬치` 하나뿐이다.

## 4. 주문 모델

주문은 **카테고리의 순서열**이다. 카테고리는 분류 꼬리표가 아니라 **주문의 단위**다.

- **카테고리별 중복 규칙.** 주력(음료·꼬치)은 순서열에 여러 번 올 수 있고,
  특선/사이드(튀김·사시미·사이드)는 한 번만 온다(3장 참조).
- **순서열이 주문 순서를 정의.** "음료 먼저 → 안주"는 순서열 맨 앞에 `음료`를 두면 표현된다.
- **주문량 차이 = 순서열 길이.** 퇴근직장인 `[음료, 꼬치, 꼬치]`(많음) vs 혼술족 `[꼬치]`(소량).

> 주문 크기 상한은 각 손님의 authored 순서열 길이가 정한다. 중복 규칙은 그 순서열 안에서
> 한 카테고리가 여러 번 올 수 있는지만 정한다. 특선·사이드는 authored 시점에 이미 1회로 제한한다.

### 재주문은 base 기능

주문열을 하나씩 밟는 것이 base 상태 머신의 기본 동작이다. 따라서 "재주문"은 별도 상태가 아니라
**주문열의 다음 슬롯으로 진행**하는 것뿐이다(6장 참조). 유형별 재주문 차이는 순서열 데이터로 끝난다.
중복 불가 카테고리(사시미·사이드)는 순서열 작성 시 최대 1회로 검증한다.

## 5. 손님 상태 (base 공통) — 5개

```
Entering ─(착석)→ Ordering ─(주문확정)→ Waiting ─(정상 서빙)→ Eating ─┐
   ▲                                        │(인내심 0)              │(식사 종료)
   │                                        ▼                       │
   └────────────── 다음 슬롯 있으면 Ordering ◀──────────────────────┘
                                            └(다음 슬롯 없으면)→ Leaving ─→ (제거)
                          Waiting(인내심 0) ─────────────────────────→ Leaving(화남)
```

| 상태 | 하는 일 | 다음 | 전이 트리거 |
|---|---|---|---|
| **Entering** 입장 | 자리로 이동, 입력 비활성 | Ordering | 이동 타이머 |
| **Ordering** 주문 | 현재 슬롯 카테고리의 메뉴를 말풍선으로 표시 | Waiting | 짧은 타이머 |
| **Waiting** 대기 | 인내심 게이지 표시, 서빙 대기 | Eating / Leaving | **서빙 이벤트**(외부) / 게이지 0 |
| **Eating** 식사 | 반응 표시 → 먹기, 만족도 확정 | Ordering(다음 슬롯) / Leaving | 식사 타이머 |
| **Leaving** 퇴장 | 팁·명성·리뷰 확정, 퇴장 이동 | 제거 | 퇴장 타이머 |

- 외부 이벤트는 `Waiting`의 서빙 **하나뿐**이고 나머지는 전부 시간 구동이다.
- `Eating` 종료 시 주문열에 다음 슬롯이 있으면 `Ordering`으로 되돌아간다(= 재주문).
- `mood`(happy / meh / angry)는 상태가 아니라 손님이 든 **데이터**다. Leaving이 이를 읽어 연출을 고른다.
- **인내심 게이지**: `Waiting → Leaving(화남)` 전이는 배선하되 `patienceEnabled=false`로 꺼둔다.

## 6. 서빙 접점 계약 (Chef → Customer)

두 클래스가 닿는 유일한 지점이므로 명시적으로 고정한다. 요리사는 **판정하지 않고 사실만** 넘긴다.

```
serve payload = { category, recipeMatched, frontResult, backResult }
                // category: 이 접시가 어느 카테고리인지 (현재 대기 슬롯과 일치해야 수령)
                // frontResult/backResult ∈ under | perfect | over | burnt (기존 DONENESS)
```

손님이 이 payload를 받아 자기 판정 규칙으로 만족도·팁·리뷰를 계산한다.

## 7. 손님 유형 로스터 (5종)

| 유형 | 주문 순서열 | 판정(judge) | 추가 상태 | 구현 형태 | 단계 |
|---|---|---|---|---|---|
| **혼술족** | `[꼬치]` | base | — | 데이터 | 1차 |
| **퇴근직장인** | `[음료, 꼬치, 꼬치]` | base | — | 데이터 | 1차 |
| **미식블로거** | `[꼬치]` | Perfect 요구 + 리뷰 산출 | — | 서브클래스(판정) | 1차 |
| **커플** | `[꼬치]` | 양면 perfect 보너스 | — | 서브클래스(판정) | 1차(스탠드인) |
| **취객** | `[음료, 음료, 음료]` | base | `Disturbing` | 서브클래스(상태) | 2차 |

순수하게 **상태를 새로 추가하는 유형은 취객 하나**다. 혼술족·퇴근직장인은 데이터, 미식블로거·커플은
판정 규칙만 다르다.

### 7.1 혼술족 — 데이터

- 순서열 `[꼬치]`. 인내심 높음·단골화 높음은 config 숫자. 소량 주문.

### 7.2 퇴근직장인 — 데이터

- 순서열 `[음료, 꼬치, 꼬치]`. "일단 생맥 → 안주 추가"가 순서열로 그대로 표현되고,
  꼬치가 중복 가능이라 "주문량 많음"이 자연히 나온다.
- 별도 `Reordering` 상태나 서브클래스가 필요 없다(주문 모델이 재주문을 base로 흡수).
- 기획서상 2인 그룹이지만 손님 1명 전제에서는 단일 엔티티로 단순화(멀티 손님 때 2인 복원).

### 7.3 미식블로거 — 판정 override + 리뷰

- 순서열 `[꼬치]`. `judge()` override: 양면 perfect가 아니면 낮게 판정.
- 리뷰를 산출해 손님/세션에 기록한다(다음 영업일 손님 수 반영은 확장). 별도 상태는 두지 않는다.

  ```
  judge(matched, f, b):
    if matched and f == 'perfect' and b == 'perfect': return GOOD
    return LOW
  ```

### 7.4 커플 — 판정 override (스탠드인)

- 순서열 `[꼬치]`. 기획서 특징인 "플레이팅 판정 가중치↑"는 플레이팅 스테이션이 없어,
  현재 모델에서는 **양면 perfect일 때 팁 보너스**로 스탠드인한다.

  ```
  judge(matched, f, b):
    base = Customer.judge(matched, f, b)
    if matched and f == 'perfect' and b == 'perfect': return bonus(base)   // 팁↑
    return base
  ```

- 2인이므로 손님 1명 전제에서는 2인 1엔티티로 모델링. 플레이팅·멀티 손님 도입 시 정식 교체.

### 7.5 취객 — Disturbing (2차, 멀티 손님 전제)

- 순서열 `[음료, 음료, 음료]`(음료 중복). `Disturbing` 상태가 **다른 손님의 대기 게이지를 감소**
  시킨다(기획서 7장). 손님 1명이면 대상이 없으므로 멀티 손님 도입 후 구현.

## 8. 클래스 구조 스케치

```js
// CATEGORY(스테이션·중복 규칙)는 짝 문서(메뉴 카테고리와 주문 규칙)가 정의한다.

class Customer {                       // base
  orderSequence   // [category, ...]   ← 유형별 데이터. 작성 시 CATEGORY.repeatable 검증
  slotIndex = 0
  patienceEnabled = false              // 지금은 인내심 감소 꺼둠
  order; satisfaction; mood; tip; seatId; review = null

  currentCategory() { return this.orderSequence[this.slotIndex]; }

  onServed({ category, recipeMatched, frontResult, backResult }) {   // 손님이 판정 소유
    if (this.state !== 'waiting') return;
    if (category !== this.currentCategory()) return;                 // 다른 메뉴 → 무시
    this.satisfaction = this.judge(recipeMatched, frontResult, backResult);
    this.mood = this.satisfaction >= GOOD ? 'happy' : 'meh';
    this.tip  = this.calcTip();
    this.setState('eating');
  }

  onEatingDone() {                     // 재주문을 base가 흡수
    if (this.slotIndex + 1 < this.orderSequence.length) {
      this.slotIndex++;
      this.setState('ordering');       // 다음 슬롯 = 재주문
    } else {
      this.setState('leaving');
    }
  }

  judge(matched, f, b) {               // base 규칙
    if (!matched) return FAIL;
    if (f === 'over' || b === 'over') return LOW;
    return GOOD;
  }
}

// 데이터 (서브클래스 아님)
const SOLO   = { type: '혼술족',   orderSequence: ['꼬치'],               patience: 'high' };
const OFFICE = { type: '퇴근직장인', orderSequence: ['음료', '꼬치', '꼬치'] };

// 서브클래스 — 판정만 다름
class FoodBlogger extends Customer {
  judge(matched, f, b) {
    if (matched && f === 'perfect' && b === 'perfect') return GOOD;
    return LOW;
  }
  // + 리뷰 산출 (상태 추가 없음)
}
class CoupleGuest extends Customer {
  judge(matched, f, b) {
    const base = super.judge(matched, f, b);
    if (matched && f === 'perfect' && b === 'perfect') return bonus(base);
    return base;
  }
}

// 서브클래스 — 상태 추가 (2차)
class DrunkGuest extends Customer {
  // orderSequence = ['음료', '음료', '음료']
  // + Disturbing 상태: 다른 손님 게이지 감소 (멀티 손님 전제)
}
```

### 전이 로직 소유

- **상태 = 행동만.** 다음 상태는 Customer가 소유한 전이 로직(주문열 진행 포함)이 결정한다.
- 유형 추가는 대부분 **순서열 데이터 한 줄** 또는 **판정 메서드 하나**로 끝난다.

## 9. 도입 단계

| 단계 | 범위 |
|---|---|
| 1차 | base 상태 머신 + 주문열 모델 + 혼술족·퇴근직장인(데이터) + 미식블로거·커플(판정). 손님 1명, 인내심 골격만. 카테고리 중 `꼬치`만 실제 구현(나머지 스테이션 미구현). |
| 2차 | 드링크·튀김 등 스테이션, 멀티 손님·좌석, 인내심 가동, 취객(Disturbing), 커플 정식(플레이팅). |

1차는 "데이터 유형 / 판정 override 유형 / (2차의) 상태 추가 유형" 갈래를 모두 설계상 커버한다.
단 실제 재주문(`[음료, 꼬치, 꼬치]`)은 드링크 스테이션이 있어야 의미가 있어, 1차에서는 순서열이
사실상 `[꼬치]`로 축약된다.
