## 목적

메뉴 항목을 **카테고리**로 정의하고, 각 카테고리의 스테이션 대응과 중복 주문 규칙을 데이터로
고정한다. 카테고리 하나가 "손님이 무엇을 주문하는가", "요리사가 어디서 만드는가", "한 손님이
몇 번 주문할 수 있는가"를 함께 규정해, 손님 시스템(`GPL-002`)과 조리 시스템이 같은 분류를
참조하도록 한다.

## 범위

### 포함

- 카테고리 5종의 정의와 스테이션 1:1 대응
- 카테고리별 중복 주문 허용 여부와 그 검증 규칙
- 주문을 카테고리의 순서열로 표현하는 규칙
- 프로토타입 메뉴의 카테고리 매핑
- 서빙 시 카테고리 전달 계약

### 제외

- 손님 유형·상태·판정(`GPL-002`)
- 판매가·팁·품질 배율 같은 밸런스 수치
- 꼬치 이외 스테이션의 조리 상호작용 구현
- 재료 재고·수량·품절 관리
- 복합 메뉴(오니기리 등)의 다공정 조합 정의

## 상세 요구사항

1. 모든 메뉴 항목은 **정확히 하나의 카테고리**를 가진다.
2. 카테고리 집합은 `음료`, `꼬치`, `튀김`, `사시미`, `사이드`로 고정하며, 각 카테고리는 하나의
   조리 스테이션과 1:1로 대응한다.

   | 카테고리 | 스테이션 | 중복 주문 |
   |---|---|---|
   | 음료 | 드링크 | 허용 |
   | 꼬치 | 꼬치(조립+구이) | 허용 |
   | 튀김 | 튀김 | 불허 |
   | 사시미 | 사시미·플레이팅 | 불허 |
   | 사이드 | 즉시제공 | 불허 |

3. 각 카테고리는 **중복 주문 허용 여부**를 속성으로 가진다. `음료`·`꼬치`는 허용, `튀김`·`사시미`·
   `사이드`는 불허한다.
4. 주문은 **카테고리의 순서열**로 표현하며, 순서열의 순서가 손님이 주문하는 순서를 정의한다.
5. 한 손님의 주문 순서열에서 **중복 불허 카테고리는 최대 1회** 나타난다. 이 조건을 위반한
   순서열은 무효로 처리하고 생성·수용하지 않는다.
6. 중복 허용 카테고리는 한 순서열에 여러 번 나타날 수 있다.
7. 조리 스테이션 라우팅은 카테고리에서 파생한다. 카테고리를 알면 어느 스테이션에서 만드는지
   결정되며, 스테이션 정보를 항목별로 중복 정의하지 않는다.
8. 요리사가 완성한 결과를 손님에게 전달할 때 **어느 카테고리인지**를 함께 전달한다. 전달 계약은
   최소 `category`를 포함한다.
9. 카테고리 정의(구성원, 스테이션 대응, 중복 허용 여부)는 **한 위치에서만** 정의하고 화면·손님
   유형별로 다시 정의하지 않는다.
10. 프로토타입 메뉴의 카테고리 매핑은 다음과 같다. 즉시제공 메뉴는 `에다마메` 대신 `양배추`를 사용한다.

    | 메뉴 | 카테고리 |
    |---|---|
    | 네기마, 모모, 츠쿠네, 카와, 난코츠, 삼겹살말이 | 꼬치 |
    | 생맥주, 하이볼, 사와 | 음료 |
    | 가라아게 | 튀김 |
    | 사시미 모듬 | 사시미 |
    | 양배추 | 사이드 |

## 예외 및 경계 조건

- 정의되지 않은 카테고리를 참조하는 메뉴·주문은 무효다.
- 중복 불허 카테고리가 두 번 이상 포함된 순서열은 데이터 검증에서 거부한다.
- 현재 구현된 스테이션은 `꼬치` 하나뿐이므로, 실제로 주문·서빙 가능한 카테고리는 `꼬치`로 한정된다.
  나머지 카테고리는 데이터 정의만 존재하고 런타임 사용은 후속 스테이션 도입 시 활성화한다.
- 전달 계약의 `category`가 손님이 현재 기다리는 슬롯의 카테고리와 다르면 그 전달은 수용되지 않는다.

## 비기능 요구사항

- 카테고리와 중복 규칙은 버전 관리가 가능한 데이터 형태로 한 곳에 정의한다.
- 잘못된 순서열(중복 불허 위반, 미정의 카테고리)은 런타임 전에 검출할 수 있어야 한다.
- 콘텐츠 작성자가 메뉴를 추가할 때 카테고리만 지정하면 스테이션·중복 규칙이 자동으로 따라와야 한다.
