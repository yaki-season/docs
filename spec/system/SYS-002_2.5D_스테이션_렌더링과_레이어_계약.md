## 목적

기존 주문·조리 상태 로직을 유지하면서 손님 정보 화면과 독립 조리 스테이션을 Three.js 기반 2.5D 장면으로 구성한다. 각 화면은 별도 카메라 프리셋을 사용하되 바 안쪽 주인공의 한 위치와 실제 가게 배치를 공유해, 손님 정면·아래쪽 불판·옆쪽 주류 도구 사이의 원근과 시선 전환이 자연스럽게 이어지게 한다.

## 범위

### 포함

- Three.js 단일 렌더러와 화면별 고정 원근 카메라 프리셋
- 독립 손님 정보 장면과 조립·그릴·주류·서빙 조리 장면
- 손님 화면의 배경·손님·바 테이블·제공 음식·전경 레이어
- 조리 화면의 스테이션·인터랙티브·VFX와 DOM 주문서·준비 목록
- 좌·우 단계 전환, 테이블 복귀와 퀵 전환
- 정적 JPG, 투명 PNG, 기존 꼬치 익힘 셰이더의 결합
- 레이아웃 안전 영역, 에셋 로딩 게이트, 저사양 폴백
- 기존 DOM 주문·안내·탭 UI와 3D 캔버스의 입력 우선순위

### 제외

- glTF 캐릭터, 스켈레탈 애니메이션과 물리 엔진
- 자유 카메라, 줌·회전 조작과 충돌 처리
- 현재 단계의 모바일 터치·크롭 최적화
- 실시간 그림자 맵, 풀스크린 포스트 프로세싱과 블룸
- 모바일 터치 최적화와 PWA

| 7 | DOM UI | 손님 상태·주문서·준비 목록·전환·결과 | 캔버스 위, 텍스트를 이미지에 굽지 않음 |

## 상세 요구사항

1. 기존 상태 원본과 조리 판정은 렌더러를 import하지 않으며 `SYS-001 v1.0.0`의 전이 함수를 유지한다.
2. 앱은 `origin/agent/yakitori-vertical-slice`의 커밋 `d3fd2c7` 또는 이를 포함한 병합 커밋을 구현 기준선으로 사용한다.
3. 화면 렌더링은 Three.js의 렌더러 하나와 `requestAnimationFrame` 루프 하나만 사용한다.
4. 모든 카메라는 바 안쪽에 선 주인공의 동일한 기준 위치에서 파생한 고정 원근 1인칭 프리셋이며 자유 조작을 제공하지 않는다.
5. 손님 정보 화면, 조립, 그릴, 주류와 서빙은 각자 독립 장면 프리셋으로 존재하고 필요한 배경·대상·인터랙션만 활성화한다.
6. 손님 정보 화면은 정면의 일렬 좌석과 바 테이블을, 그릴은 고개를 숙인 아래쪽 작업대를, 주류 화면은 실제 배치 방향으로 고개를 돌린 작업대를 보여준다.
7. 화면 전환은 좌·우 단계 이동과 퀵 전환을 모두 지원하며, 카메라 연출 중에도 주문·조리·준비 상태를 유지한다.
8. `1920×1080`에서 손님 화면은 얼굴·상태·테이블 음식 안전 영역을, 조리 화면은 상단 주문서·중앙 작업·하단 준비 목록 안전 영역을 각각 유지한다.
9. 생성 에셋의 논리 기준 캔버스는 `2048×1152`이며 최종 합성은 `16:9`, `1920×1080 FHD` Chrome 화면에서 검수한다.
10. 화면별 카메라 높이·화각·회전·소실점을 제작 전에 숫자로 확정하는 것을 완료 조건으로 요구하지 않는다. 승인된 통합 원본 장면에서 측정한 anchor·투영값을 companion metadata로 기록할 수 있다.
11. 투명 PNG는 알파 테스트나 일반 알파 블렌딩으로 표시하고 불투명 픽셀의 검은·녹색 테두리가 보이지 않게 한다.
12. 배경과 전경은 포인터 이벤트를 받지 않으며 인터랙티브 오브젝트만 레이캐스트 대상으로 등록한다.
13. 재료·접시처럼 작은 그림의 실제 클릭 영역은 시각 바운드보다 확장해 최소 `44×44 CSS px`를 충족한다.
14. 꼬치는 기존 면별 익힘 시간에서 계산한 값으로 텍스처 또는 `uDoneness`를 갱신한다.
15. 손님 텍스처는 `considering`, `order-ready`, `waiting`, `urgent`, `receiving`, `eating`, `drinking`, `disappointed`, `angry`, `leave` 등 승인된 상태 ID로 교체하고 게임 로직이 파일 경로를 직접 조합하지 않는다.
16. 제공 음식·음료와 빈 식기는 손님 좌석별 바 테이블 anchor에 접지하고 손님 신체·테이블과 같은 소실점 및 가림 순서를 사용한다.
17. 조리 화면의 상단 주문서와 하단 준비 목록은 DOM UI로 렌더하고 3D 캔버스의 조작 대상을 가리지 않는다.
18. 모든 필수 에셋은 명시적 manifest에서 로드하고 하나라도 실패하면 빈 캔버스 대신 오류와 다시 시도를 표시한다.
19. 로딩 중과 브라우저 숨김 상태에서는 렌더 루프를 정지하며 재개 시 큰 델타를 한 프레임에 적용하지 않는다.
20. 초기 장면은 외부 URL, API 키와 원격 폰트 없이 로드 가능해야 한다.
21. 손님 스프라이트는 손님 화면의 바 카운터 뒤에 배치해 하체가 상판에 가려지고 얼굴과 손은 필요 상태에서 보이게 한다.
22. 조리 도구는 설정상 바 테이블의 플레이어측에 바로 붙은 작업 공간으로 인식되어야 하며 화면별 원근이 독립된 빈 방처럼 보이면 승인하지 않는다.
23. 주인공 얼굴·몸은 영업 장면에 렌더하지 않고, 손은 별도 승인 에셋이 있을 때만 플레이어측 하단 레이어에 표시한다.

## 성능 예산

- 기준 데스크톱 `1280×720`에서 평균 30 FPS 이상을 유지한다.
- 드로우콜은 단일 손님·단일 작업대 장면에서 20 이하를 목표로 하고 30을 넘지 않는다.
- 삼각형은 10,000 이하를 목표로 하고 50,000을 넘지 않는다.
- 실시간 광원은 ambient와 숯불 보조광을 합쳐 2개 이하로 제한한다.
- 연기 쿼드는 6장 이하, 동시 파티클은 80개 이하로 제한한다.
- `devicePixelRatio`는 1.5를 상한으로 한다.
- 초기 장면에 필요한 압축 전송 에셋은 2.5MB 이하, 전체 이번 범위 에셋은 5MB 이하를 목표로 한다.
- 실시간 그림자 맵 대신 접지 그림이 포함된 스프라이트 또는 반투명 쿼드를 사용한다.

## 예외 및 경계 조건

- WebGL2 또는 Three.js 초기화에 실패하면 기존 DOM 기능 화면으로 폴백하거나 지원 불가 오류를 명시한다.
- 에셋 비율이 뷰포트와 다르면 중앙 크롭을 사용하되 활성 화면의 손님·주문서·작업·준비 목록 안전 영역을 자르지 않는다.
- 스테이션 전환 중 새 전환 요청은 마지막 유효 프리셋 하나로 수렴하고 카메라가 중간 위치에 고정되지 않는다.
- 창 크기 변경 중 선택·드래그 상태가 있다면 논리 상태를 보존하고 새 카메라 기준으로 클릭 영역을 다시 계산한다.

## 비기능 요구사항

- 레이어, 프리셋, 에셋 경로와 앵커는 한 설정 모듈에서 조정 가능해야 한다.
- 렌더러 교체가 상태 전이 테스트를 깨뜨리지 않아야 한다.
- 장면의 텍스트는 DOM으로 제공해 생성 이미지의 오탈자에 의존하지 않는다.
- 에셋 라이선스와 생성 근거는 `app/art/gameplay/ASSET-MANIFEST.md`에 기록한다.

## 완료 기준

- [ ] Three.js 단일 렌더러에서 손님 정보 화면과 각 조리 화면이 독립 프리셋·레이어 순서로 표시된다.
- [ ] 손님 화면에서 손님·주문 상태·제공 음식·빈 식기가 좌석별로 명확히 대응한다.
- [ ] 조리 화면에서 상단 좌석 순서 주문서, 중앙 조리 도구와 하단 준비 목록이 겹치지 않는다.
- [ ] 손님 정면, 아래쪽 그릴과 옆쪽 주류 프리셋이 같은 바 안쪽 주인공 위치와 실제 공간으로 이어져 보인다.
- [ ] 화면별 바 테이블·작업 표면·음식·도구의 원근과 소실점이 어긋나지 않는다.
- [ ] 기존 조립·굽기·서빙 판정과 자동 테스트가 회귀 없이 동작한다.
- [ ] 모든 에셋이 manifest 경로에서 로드되고 실패 상태가 검증된다.
- [ ] 두 기준 뷰포트에서 손님, 주문 UI와 작업 대상이 가려지거나 잘리지 않는다.
- [ ] 드로우콜, 삼각형, DPR과 초기 에셋 예산이 기록된다.
- [ ] 캔버스가 비어 있거나 단색인 상태와 처리되지 않은 콘솔 오류가 없다.
