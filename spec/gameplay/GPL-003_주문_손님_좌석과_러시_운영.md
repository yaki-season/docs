## 목적

손님 입장부터 메뉴 고민, 주문 접수, 부분 서빙, 식사, 퇴장과 좌석 정리까지의 운영 규칙을 정의한다. 플레이어가 여러 손님을 동시에 관리하되 실패 원인을 예측할 수 있고, 품질·팁·만족도·명성이 서로 중복 계산되지 않게 한다.

## 범위

### 포함

- 1인 손님과 2인 그룹의 좌석 배정·퇴장
- 주문 전·주문 중·주문 수령 대기·주문 수령 상태
- 부분 서빙, 대기 시간 회복, 만족도·추가 주문과 팁
- 일반·단골·특수 손님 유형
- 러시아워 주문 파동과 화면 밖 위험 우선순위
- 빈 접시·잔과 좌석 정리

### 제외

- 정확한 손님 생성 간격과 확률 수치
- 개별 캐릭터의 대사와 초상 제작 규격
- 3~4인 일반 그룹과 8인 단일 그룹 표현
- 온라인 대기열 또는 다른 플레이어와의 경쟁

## 상태 모델

### 좌석 상태

```text
비어 있음 → 자동 예약됨 → 착석 → 주문 전 → 주문 중
→ 주문 수령 대기 → 식사 중 → 퇴장 대기
→ 정리 필요 → 비어 있음
```

### 손님 상태

```text
입장 → 착석 → 주문 전(4~6초) → 주문 중(주문서 아이콘)
→ 주문 수령 대기 → 주문 수령 → 식사·음주
→ 추가 주문 또는 계산 → 그룹 퇴장 → 종료
```

### 주문 상태

```text
메뉴 결정 → 접수 대기 → 접수 완료 → 제작 중 → 완성 대기
→ 부분 제공 → 모든 항목 제공 완료
                   ↘ 실패·재조리 ↗
```

## 상세 요구사항

### 좌석과 그룹

1. 기본 가게는 카운터 6석으로 시작하고 인테리어 업그레이드로 8석을 거쳐 최대 12석까지 확장할 수 있다.
2. 혼술족은 빈 좌석 하나에만 앉는다.
3. 퇴근 직장인은 2인 그룹으로 생성하며 인접한 빈 좌석 두 개가 있을 때만 함께 입장한다.
4. 2인 그룹의 주문, 대기 게이지와 만족도는 손님별로 관리한다.
5. 2인 그룹은 두 손님이 모두 식사와 추가 주문을 끝냈을 때 함께 퇴장한다.
6. D30의 8인 예약과 2인 그룹 네 팀·대규모 일행의 표현은 1차 배포 범위에서 제외한다. 가게 확장 시나리오를 설계하는 출시 후 단계에서 좌석 수·그룹 모델·예약 흐름을 함께 결정한다.
7. 퇴장한 좌석에는 손님별 빈 접시·잔이 남고 좌석별 정리 입력이 끝날 때까지 새 손님을 배정하지 않는다.
7-1. 정리 필요 좌석은 해당 좌석을 `3초` 연속 누르고 유지해 정리한다. 누르는 동안 빈 식기 위에 정리 아이콘과 치우는 모션, 누적 시간을 나타내는 원형 진행 게이지를 함께 표시한다.
7-2. 원형 게이지가 가득 차면 빈 접시·잔과 정리 오버레이를 제거하고 좌석 상태를 `비어 있음`으로 전환한다. 이 시점부터만 입장 시스템이 그 좌석을 다음 손님 또는 그룹의 후보로 사용한다.
7-3. 누르기를 3초 전에 놓거나 `pointercancel`·포커스 상실이 발생하면 정리 모션과 게이지를 즉시 멈추고, 다음 시도는 0초부터 다시 시작한다. 이는 `연속 3초 유지` 조건을 명확히 하기 위한 P0 기본 계약이다.
7-4. 홀 담당을 고용한 경우 손님 또는 동행 그룹의 퇴장 직후 좌석 정리를 자동 시작하고 `3초` 뒤 완료한다. 이는 플레이어의 3초 홀드 정리를 대체하는 직원 자동화이며, 정리 완료 뒤 해당 좌석을 다음 손님 후보로 사용한다.
8. 직원의 홀 자동화가 활성화되면 서빙과 좌석 정리를 대신할 수 있으나 진행 상태는 플레이어 직접 처리와 같은 계약을 사용한다.
9. 플레이어는 손님의 좌석을 직접 선택하거나 안내하지 않는다.
10. 시스템은 전체 빈자리 수와 연속된 빈자리 수를 함께 검사해 손님 또는 그룹의 입장을 결정한다.
11. 그룹 인원수만큼 빈자리가 있어도 연속된 좌석이 부족하면 해당 그룹은 입장시키지 않으며 분리 착석시키지 않는다.
12. 입장 가능한 그룹은 조건을 충족하는 연속 좌석에 시스템이 자동 배치한다.

### 주문과 식별

13. 주문은 주문자, 좌석, 그룹, 메뉴, 수량, 취향, 생성 시각과 현재 상태를 가진다.
14. 손님은 착석 뒤 영업일 데이터 `timingSec.orderThinkMin=4초`와 `orderThinkMax=6초` 사이에서 균등 무작위로 뽑은 시간 동안 주문 전 상태에서 메뉴를 고민하며 머리 위에 `...` 아이콘 또는 동등한 애니메이션을 표시한다. 재주문도 같은 규칙으로 새 시간을 뽑는다.
15. 메뉴를 결정한 손님은 주문 중 상태로 전환하고 머리 위에 클릭 가능한 주문서 아이콘을 표시한다.
16. 플레이어가 주문서 아이콘을 클릭하면 주문 내용을 공개하고 손님을 주문 수령 대기 상태로 전환한다.
17. 접시·잔과 손님 주문 매트는 같은 `색상+도형+좌석 번호` 표식을 사용한다.
18. 색상만으로 주문을 구분하지 않는다.
19. 직장인 2인은 D1에서 생맥주를 먼저 주문하고 이후 안주를 개별 또는 추가 주문할 수 있다.
20. 같은 메뉴를 묶음 조리하더라도 완성 결과는 주문 식별자별 접시·잔에 연결하지 않고 공용 준비 목록에 보관한다.
21. 플레이어는 손님 화면 하단의 공용 완성품 카드를 손님에게 드래그해 제공한다. 시스템은 대상 손님의 메뉴·조리 방식이 일치하고 남은 수량이 있는 주문 항목에 한 개를 배정하며, 같은 손님에게 일치 항목이 여러 개면 먼저 접수된 주문부터 처리한다.
22. D1 첫 손님 `REGULAR_TSUKIOKA`의 주문 `D1-ORDER-001`은 네기마 3개와 생맥주 1잔 한 건으로 생성한다. 생맥주를 먼저 제공해도 같은 주문의 네기마 3개는 미완료 항목으로 남아, 부분 수령 대기와 완료 수령의 차이를 보여 준다.

### 대기·만족도·수익 역할 분리

22. 대기 게이지는 플레이어가 주문서 아이콘을 클릭해 주문을 접수한 시점부터 손님별로 감소한다.
22-1. 현재 후보 밸런스 기준에서 단골이 아닌 모든 일반 손님 유형의 기본 대기 시간은 `60초`, 단골 손님의 기본 대기 시간은 `100초`다. 손님별 대기 게이지는 이 값을 최대치로 시작한다.
22-2. `REGULAR_TSUKIOKA`의 `REGULAR`은 서사상 인물 식별자이며, 대기 시간 분류에서는 단골 손님으로 취급해 `100초`를 사용한다. 일반 손님과 단골의 향후 세부 보정은 이 기준값을 덮는 데이터 필드로만 추가한다.
22-3. `60초`와 `100초`는 실제 개발·플레이테스트 이후 조정할 후보값이다. 코드 상수나 화면 문구로 고정하지 않고 `DAT-001` 손님 유형 데이터의 `patienceSec`에서 읽는다.
23. 주문한 모든 음식을 한 번에 전달할 필요는 없으며 완성된 항목부터 부분 서빙할 수 있다.
24. 주문 항목 하나를 전달할 때마다 해당 손님의 대기 게이지를 영업일 데이터 `waitRecoverySec`만큼 회복한다. 현재 후보값은 메뉴 종류와 무관하게 `10초`다.
25. 일부 항목만 전달된 손님은 주문 수령 대기 상태를 유지하고 완료 항목과 미완료 항목을 별도로 기록한다.
26. 모든 주문 항목을 전달하면 손님은 주문 수령 상태로 전환하고, 손님 유형과 관계없이 `15초` 동안 식사·음주 애니메이션을 표시한다.
26-1. 단, `Fail` 품질 항목을 하나라도 수령한 손님은 그 즉시 빈 식기·잔을 남기고 화난 퇴장한다. 같은 주문의 미제공 항목은 취소하고 이미 제공한 항목의 판매 기록은 유지한다. 이 경우 식사·음주 애니메이션, 추가 주문, 팁, 만족도·긍정 명성 보상을 만들지 않으며 명성 `-1`을 한 번 기록한다. 양면이 모두 탄 완전 탄 음식은 제공할 수 없으므로 이 규칙의 대상이 아니다.
26-2. 2인 그룹에서 한 명이 `Fail` 항목을 수령하면 두 명 모두 즉시 그룹 퇴장한다. 두 사람의 미제공 항목은 함께 취소하고 이미 제공한 항목의 판매 기록만 유지하며, 그룹은 식사·음주·추가 주문·팁·만족도·긍정 명성 보상을 만들지 않는다. 화난 퇴장 명성 `-1`은 그룹 공통 원인으로 한 번만 기록한다.
27. `15초`가 끝나면 손님은 추가 주문 판정을 한 번 수행하고, 추가 주문이 없으면 빈 그릇·빈 컵을 남기고 퇴장한다. 추가 주문이 있으면 새 주문 상태로 전환한다. 현재 후보값에서 만족도 `100%`인 주문은 `40%`, `70~99%`인 주문은 `20%`, `70%` 미만 주문은 `0%` 확률로 재주문한다.
28. 대기 게이지가 0이 되면 해당 손님은 제공받지 못한 주문을 취소하고 실망 또는 분노 반응과 매출 0·명성 `-1` 원인을 남긴 뒤 퇴장한다.
29. 2인 그룹에서 한 명의 대기 게이지가 0이 되면 동행 두 명 모두 즉시 그룹 퇴장으로 전환한다. 두 손님의 미제공 항목은 함께 취소하고, 이탈 원인·명성 영향은 공통 그룹 식별자로 한 번만 기록한다.
29-1. 그룹 퇴장 전에 이미 제공 완료된 항목의 제공 기록과 판매가는 유지하되, 그룹은 추가 주문·팁·만족도 보상을 만들지 않고 퇴장한다.
30. 1차 밸런스에서 정상 수령으로 완료한 주문의 기본 팁은 손님 유형·대기 게이지 잔량과 무관하게 `2G`다. 대기·유형 보정은 플레이테스트 이후로 미루며, 기억 주문의 정답·정상 수령 보너스 팁은 이 기본 팁과 별도 원인으로 한 번만 더할 수 있다.
31. 조리 품질은 판매가와 항목별 만족 점수에 적용한다. 만족 점수는 판매가와 별도 계산이며 팁에는 직접 적용하지 않는다.
32. 주문 만족도는 모든 제공 항목의 품질 만족 점수를 수량 단위로 평균 내어 소수점을 버린 백분율이다. 현재 후보값은 `Perfect=100`, `Good=40`, `OK=10`, `Fail=0`이다. 예를 들어 Perfect 2개와 Good 1개면 `floor((100+100+40)/3)=80%`다.
33. 만족도는 추가 주문 확률과 명성 획득에만 직접 영향을 준다. 주문 만족도 `100%`는 명성 `+3`, `80~99%`는 `+1`, 그 미만은 `0`이다. 대기 시간 초과·미제공 취소·Fail 즉시 퇴장은 만족도 산정·긍정 보상·재주문 대상이 아니며, Fail 즉시 퇴장은 화난 퇴장으로 명성 `-1`을 남긴다.
34. 재주문 확률 `100% 만족=40%`, `70~99% 만족=20%`, `70% 미만=0%`은 플레이테스트로 조정할 `candidate` 수치다. 재주문 판정은 식사·음주 `15초` 종료마다 한 번만 수행한다.

### 단골과 기억 주문

35. 같은 인물이 만족스러운 **전체 주문**을 5회 완료하면 단골로 전환한다. 전체 주문은 그 주문의 모든 항목을 제공한 뒤 만족 반응이 확정된 경우이며, 부분 서빙 항목 수는 별도로 누적하지 않는다.
35-1. 2인 그룹의 동행 만족 결과는 각 인물의 단골 전환 횟수에 중복 합산하지 않는다.
36. 츠키오카는 D7 종료 시 첫 단골로 기록하고 D8부터 `늘 먹던 걸로` 주문을 사용한다. 이 전환은 시나리오 고정 사건으로, 일반 손님의 5회 전환 횟수와 별개다.
37. 단골 노트는 손님별 방문 기록으로 시작하며, 확인하지 못한 메뉴·소스·음료는 숨긴다. 기억 주문을 **정답으로** 마친 방문의 실제 주문만 한 항목으로 기록해, 방문을 거듭할수록 노트가 채워진다.
38. `늘 먹던 걸로` 기억 주문이 실제 선호와 틀리면 일반 조리 품질과 분리된 `취향 불일치` 반응을 기록한다. 손님은 궁시렁대며 해당 주문을 먹고, 주문 수령·식사·퇴장 흐름은 계속한다. 이 오답 주문은 단골 노트에 기록하지 않으며, 조리 품질 평균과 관계없이 주문 만족도를 일괄 `30%`로 처리한다.
39. 기억 주문의 모든 메뉴·소스·음료를 맞히고, 그 주문의 모든 항목을 대기 시간 초과 없이 정상 수령하면 `기억 주문 정답` 보너스 팁 `6G`를 한 번 지급하고 해당 실제 주문을 단골 노트에 기록한다. 이 팁은 기본 팁과 별도 원인으로 한 번만 더한다.
40. 같은 기억 주문을 세 번 틀리면 손님이 해당 방문에 한해 전체 주문을 다시 말한다. 이 재고지는 정답 추측·단골 노트 기록·보너스 팁 조건을 충족하지 않는다.
40-1. 단골 노트는 광고나 유료 재화 없이 열람할 수 있으며, 이미 기록된 방문 정보만 보여 준다.

### 러시와 위험 우선순위

41. 주문은 영업일 데이터의 파동 단위로 생성해 회복 구간 없이 지속적으로 몰리지 않게 한다.
41-1. 활성 주문은 접수 완료 뒤 모든 항목이 제공되거나 취소될 때까지 남아 있는 주문을 뜻한다. 위험 공정은 현재 진행 중이며 지정된 위험 임계값 안에 들어온 조리 항목을 뜻한다. 두 수는 손님 수·그릴 슬롯 수와 별도로 매 프레임 데이터 기준으로 계산한다.
41-2. 영업일 후보 상한은 `GPL-002 v1.7.0`의 시간대·난이도 프로파일을 사용한다. D1 첫 주문은 활성 주문 1·위험 공정 1, D1 나머지는 2·1, D2~D3은 2·2, D4~D7은 3·2, D8~D14는 3·3, D15~D29는 4·3, D30은 4·4를 상한으로 한다.
41-3. 상한값은 실제 개발·플레이테스트로 바꿀 `candidate` 값이다. 생성기는 상한을 넘는 신규 주문·위험 공정을 강제로 만들지 않고, 다음 시간대 또는 안전 상태까지 입장·주문 시점을 지연한다.
42. 조리 실패 임박은 조리 화면의 전체 화면 테두리 점등으로 알린다. 위험 대상·아이콘·경고음 등 비색상 보조 신호를 함께 제공하되, 손님 이탈·주문 알림과 같은 자리에서 경쟁시키지 않는다.
43. 손님 이탈 임박은 조리 화면 상단의 해당 주문 박스 테두리를 반복 점등해 알린다. 대기 게이지가 영업일 데이터 `urgentThresholdSec=15초`에 도달하면 느린 점등을 시작하고, 해당 주문 박스 안에 이탈까지 남은 시간 게이지를 함께 표시한다. 동시에 임박한 주문은 모두 각자 점등·게이지를 유지한다.
44. 일반 주문이 새로 발생했을 때 플레이어가 손님 화면에 있지 않으면, 조리 화면 상단의 해당 주문 박스에 `!` 표식을 표시한다. 손님 화면에서는 해당 손님의 주문서 상태로 직접 알린다.
45. 조리 실패 임박·손님 이탈 임박·일반 주문 알림은 위 위치에서 동시에 유지하며 단일 우선순위로 교대·축약하지 않는다.
46. 위험 스테이션으로 복귀하면 대상 공정을 0.4초 동안 자동 강조한다.
47. 대규모 파동도 시스템이 정한 활성 위험 수 상한을 넘기지 않도록 추가 주문 시점을 지연한다.

## 예외 및 경계 조건

- 인접 좌석이 없으면 2인 그룹은 좌석이 생길 때까지 대기하거나 생성 자체를 지연하며 분리 착석시키지 않는다.
- 손님이 먹는 중 브라우저가 백그라운드로 가면 대기·식사·추가 주문 타이머를 모두 멈춘다.
- 부분 서빙 애니메이션 중 빠른 이중 입력은 한 번의 항목 제공과 한 번의 시간 회복만 만든다.
- 주문 전·주문 중 상태에서는 대기 게이지를 감소시키지 않는다.
- 재조리 중인 주문의 원래 손님과 좌석 식별자는 유지한다.
- 특수 손님 유형이 비활성화된 빌드에서는 같은 날짜의 핵심 사건을 혼술족 또는 직장인으로 대체한다.

## 비기능 요구사항

- 좌석·손님·주문은 별도 식별자를 가져 복수 주문 상태가 서로 덮어쓰이지 않아야 한다.
- 손님 생성과 추가 주문 확률은 테스트용 시드로 재현 가능해야 한다.
- 대기 위험은 색상, 형태와 음향 중 최소 두 가지 방식으로 전달한다.
- 손님 유형은 성별·연령·직업과 음주에 대한 고정관념을 실패 연출로 사용하지 않는다.
