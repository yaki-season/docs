## 목적

최소 수직 슬라이스를 넘어 전체 30일 캠페인의 기능, 상태 일관성, 저장·복구, 반응형·접근성, 콘텐츠, 성능과 출시 정책을 검증하는 기준을 정의한다. 검증은 문서·파일명·구현 세부를 보존하는 절차가 아니라 실제 플레이 기능의 회귀를 빠르게 찾고 수정 범위를 좁히는 개발 도구여야 한다.

## 검증 파이프라인·gate 유효성 원칙

1. 필수 gate는 구체적인 사용자 행동, 저장 결과 또는 사용자 노출 품질 위험과 직접 연결해야 한다. 작업 문서의 산출물 형식, 과거 파일명, 제거된 UI 내부 구조만 보존하는 검사는 필수 gate가 될 수 없다.
2. 핵심 종단 검사는 공개 진입점에서 실제 포인터·키보드 입력으로 `시작→조리→서빙→정리→마감→정산→저장` 결과를 확인한다. 모의 시계는 대기 단축에 사용할 수 있지만 `dockAdd`, 상태 직접 대입, 성공 명령 직접 dispatch처럼 핵심 행동의 성공 결과를 만들어 내는 디버그 훅은 해당 종단 시나리오의 합격 근거로 사용할 수 없다.
3. 테스트 실패는 `제품 회귀`, `테스트 계약 낙후`, `환경/플레이크`로 먼저 분류한다. 제품 동작이 새 정본과 일치하는데 과거 파일명·DOM·renderer 내부를 기대한 실패는 출시 차단으로 집계하지 않고 같은 변경에서 테스트를 수정하거나 삭제한다.
4. 필수 gate마다 결함을 의도적으로 주입했을 때 실패하고 복구 뒤 통과한 증거, 또는 동등한 실패 민감도 검증이 있어야 한다. 계속 통과하지만 실제 결함을 잡지 못한 gate는 제거·교체 대상으로 본다.
5. 중복 검사는 유지 비용보다 독립적으로 잡는 결함이 명확할 때만 둔다. 공개 경로와 별개인 실험·레거시 진입점 검사는 공개 완료를 차단하지 않는다.
6. placeholder 수, 산출물 개수, 특정 브라우저 이름과 사람 참여 인원은 그 자체로 기능 완료 gate가 아니다. 실제 공개 화면의 누락·오해·조작 불가·지원 환경 결함과 연결될 때만 차단하며, 그 외에는 측정 위험으로 보고한다.
7. 관찰 플레이테스트는 조작성·이해도 개선을 위한 진단 입력이다. 별도 사용자 결정으로 출시 조건에 지정되지 않은 한 사람 대기만으로 구현 완료나 다음 개발 착수를 막지 않는다.

### D1 명령어 계약

- `npm run verify`는 `verify:d1-core`와 같으며, D1 release drift·핵심 도메인/시간축·공개 화면 실제 입력만 필수 차단한다.
- `npm run verify:full-diagnostic`는 저장소 전체의 asset/reference/Vitest/Playwright를 조사하는 비차단 진단이다.
- 전체 진단 실패는 공개 D1 사용자 경로와 직접 연결된 `제품 회귀`로 재현될 때만 필수 gate로 승격한다.

## 자동 기능 검증

### 상태·입력

1. 모든 애플리케이션·영업일·손님·주문·조리 상태의 허용 전이와 금지 전이를 검증한다.
2. 빠른 이중 클릭·탭이 재료 이중 삽입, 이중 뒤집기, 이중 서빙, 이중 정산과 이중 구매를 만들지 않는지 검증한다.
3. 포인터 취소·포커스 상실·스테이션 전환이 물건과 액체를 마지막 유효 상태로 복구하는지 검증한다.
4. 조리·대기 판정은 모의 시계로 모든 경계 바로 전·경계·바로 뒤 값을 검증한다.
5. 동일 데이터·입력·시드가 같은 손님·주문·경제 결과를 만드는지 검증한다.

### 조리·손님·경제

6. 네기마 순서, 잘못된 재료, 마지막 재료 제거와 조립 완료를 검증한다.
7. 그릴 앞·뒷면 독립 익힘, 화력 보정, 조기 뒤집기 복구, 과다·탄 상태를 검증한다.
8. 생맥주 홀드·릴리스, 중단·재개, 맥주·거품 목표, 넘침 차단과 재제작을 검증한다.
9. 완성품과 주문 표식, 오서빙 방지, 맛보기와 품질 반응 순서를 검증한다.
10. 1인·2인 그룹의 좌석·개별 주문·공동 퇴장·정리 후 재배정을 검증한다.
11. 품질은 판매가, 대기는 팁, 만족도는 추가 주문·명성에만 반영되는지 검증한다.
12. 콤보 팁 `x1.5`, 주문 최종 수익 `x2.0` 상한과 정산 반올림을 검증한다.
13. 직원 결과가 주문과 연결되고 속도·품질 상한·급여·숙련을 중복 적용하지 않는지 검증한다.

### 캠페인·데이터

14. S0, D1~D30과 D31의 진입·종료·대체 흐름을 전부 순회한다.
15. 각 날짜의 필수 메뉴·손님·직원 잠금 조합에도 대체안으로 진행되는지 검증한다.
16. D30 낮은 성과와 정상 성과 모두 결말·정산·D31로 연결되는지 검증한다.
17. 데이터의 중복 ID, 누락 참조, 범위 역전, 도달 불가 해금, 경제 상한 위반과 에셋 누락을 빌드 전에 검출한다.

## 저장·복구 검증

18. day-start와 day-complete 저장의 생성·로드·교체를 검증한다.
19. 영업 중 새로고침은 day-start, 정산 완료 뒤 새로고침은 다음 날에서 재개되는지 검증한다.
20. 정산·구매 중단과 재시도에서 보상·비용이 한 번만 적용되는지 검증한다.
21. 현재·이전 스키마 저장의 순차 마이그레이션과 미래 버전 거부를 검증한다.
22. 잘린 저장, 잘못된 JSON 상당 데이터, 누락 ID, 저장 공간 부족과 백업 복구를 검증한다.
23. 설정 저장이 캠페인 저장 손상과 독립적으로 복구되는지 검증한다.

## 브라우저 종단 시나리오

### D1 전체 루프

1. S0 스킵과 비스킵 양쪽으로 가게를 연다.
2. 숯을 점화하고 츠키오카 네기마를 조립·굽기·서빙한다.
3. 직장인 2인에게 생맥주 두 잔을 제공하고 추가 네기마와 화면 밖 경고를 처리한다.
4. 세 좌석의 식기를 개별 정리하고 정산·모모 복원·D2 저장을 확인한다.
5. 전체 길이가 스토리 포함 8분을 넘는지 기록한다.
5-1. D1~D3와 이후 구현되는 모든 영업일에서 마지막 계획 손님 정리 뒤 조기 자동 마감하며, 중간에 착석 손님이 0명이 된 경우 입장 가능한 다음 손님이 퇴장 완료 시점부터 13초 이내 도착하는지 실제 런타임으로 검증한다. 각 영업일의 정본 데이터·release definition에 정책이 존재하는지 검사하고, 누락·14초 등 변조된 값이 스키마와 런타임 로더 양쪽에서 거부되는 음성 사례를 유지한다. D1 시계는 17:30~02:30을 사용한다.
5-2. 포커스 상실·브라우저 숨김 동안 영업, 다음 입장, 손님, 그릴 양면, 뒤집기, 액체, 좌석 정리와 렌더 루프가 모두 정지하고 복귀 뒤 숨김 경과를 적용하지 않는지 실제 경과 대기로 검증한다.

### 운영·성장

6. D3의 그릴·드링크 교차, D7의 첫 만석, D8·D11의 기억 주문을 검증한다.
7. D18의 직원 배치, D20 리뷰, D21 자동화와 D25 직원 교육을 검증한다.
8. D26~D30 예약 준비·대체 메뉴·2인 그룹 네 팀·마지막 주문과 결말을 검증한다.
9. 일반 영업일 샘플이 준비부터 다음 목표까지 4~6분인지 기록한다.

### 입력 환경

10. PC 마우스와 모바일 한 손가락 각각으로 핵심 흐름을 완료한다.
11. 오른손·왼손 모드, 큰 터치 영역, 초보 보조, 무음과 진동 끔을 조합해 진행한다.
12. 터치 중 화면 가장자리·브라우저 UI·회전·백그라운드 진입을 재현한다.

## 시각·오디오 검수

- PC `1280x720`, `1920x1080`과 확정 모바일 기준 뷰포트에서 화면을 캡처한다.
- 각 스테이션의 대기·조작·위험·완료·실패 상태, 정산·성장·노트와 주요 스토리 장면을 캡처한다.
- HUD, 손님, 말풍선, 작업 대상, 전경과 결과가 겹치거나 잘리지 않아야 한다.
- 2D 배경과 3D 오브젝트의 앵글·접지·광원·픽셀 크기가 어긋나지 않아야 한다.
- 모든 영업 캡처는 바 안쪽 주인공 시점에서 카운터 너머 손님을 바라보며, 손님 하체가 고정 상판에 가려지고 플레이어측 작업대가 하단에 있어야 한다.
- 조립·그릴·드링크·서빙 전환과 PC·모바일 크롭 뒤에도 고정 카운터가 좌우로 이어지고 손님 얼굴·주문·반응이 유지되어야 한다.
- 플레이어 앞 완전한 손님용 스툴 열, 손님 없는 독립 작업대와 손님측에서 주방을 보는 역방향 카메라는 시각 검수 실패다.
- 생성 이미지의 잘못된 문자, 이전 `鳥屋/Toriya`, 워터마크와 콘셉트 번호가 없어야 한다.
- 주요 인물은 상태·날짜가 바뀌어도 얼굴·복장·앵커 정체성을 유지해야 한다.
- 익힘·대기·주문·위험은 색각 차이와 무음 상태에서도 구분되어야 한다.
- BGM·조리·군중음 속에서 설정된 우선순위의 가장 임박한 경고가 들리고 반복음이 폭주하지 않아야 한다.

## 출시 정책 게이트

- 최소 브라우저·기기 목록이 확정되지 않으면 호환성 검증을 완료로 표시하지 않는다.
- 주류 표현의 연령·지역 기준과 광고·IAP 정책이 확정되지 않으면 해당 기능을 출시 범위에 포함하지 않는다.
- 실제 분석 수집이 추가되면 동의·개인정보·보관 정책 검증을 별도 요구한다.
- 관찰 플레이테스트 표본이 부족하면 사용성 지표의 신뢰 구간을 미측정 위험으로 남긴다. 별도 출시 결정에서 최소 표본을 필수로 지정하지 않은 한 구현 완료와 다른 독립 개발을 차단하지 않는다.

## 예외 및 경계 조건

- 자동 테스트는 실제 대기 대신 모의 시계를 사용한다.
- 외부 폰트·오디오 실패가 핵심 조리 흐름을 막으면 차단 결함이다.
- 실기기 성능을 측정하지 못하면 데스크톱 결과로 대체하지 않고 미검증 위험으로 남긴다.
- 플레이테스트의 장애·보조 기술 요구에 맞춘 대체 입력을 제공하고 결과를 별도 기록한다.

## 비기능 요구사항

- 자동 테스트는 실행 순서와 네트워크에 의존하지 않고 반복 가능해야 한다.
- 테스트 데이터는 실제 상태 전이·판정·경제 함수를 사용해야 한다.
- 검증 명령, 기기·브라우저, 시드, 캡처와 결과를 `app`에 기록한다.
- 출시 보고서는 미해결 질문과 미측정 위험을 성공 항목과 분리한다.
