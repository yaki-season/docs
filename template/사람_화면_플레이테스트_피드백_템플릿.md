# 사람 화면 플레이테스트 피드백 템플릿

자동 테스트는 실제 사람이 화면을 보고 이해하고 조작할 수 있는지를 대신하지 않는다. PM은 각
스테이지의 중간 slice와 전체 구동 gate에서 이 양식을 채운 테스트 카드를 먼저 제공하고, 테스터의
명시적 판정을 원문 그대로 연결한다.

## PM이 먼저 제공할 테스트 카드

```text
테스트 ID:
스테이지·시나리오:
검수 화면·상태:
후보 asset ID/revision(해당 시):
정적 URL:
build/commit/manifest SHA:

시작 저장 상태: 새 게임 | 초기화 | 재개 | 파일 import
이번 테스트의 시작 조건:
이번 테스트의 종료 조건:
조작 순서:
1.
2.
3.
꼭 확인할 항목:
알려진 제외·미완성:
진단 정보 복사/다운로드 방법:
```

## 공통 확인표

- [ ] 클릭 또는 키보드 입력의 대상과 결과를 예상할 수 있었다.
- [ ] FHD/720에서 UI·아트가 겹치거나 잘리지 않았다.
- [ ] placeholder와 정식 아트를 혼동하지 않았다.
- [ ] 상태 변화가 색만이 아니라 형태·문맥으로도 구별됐다.
- [ ] 이야기 순서·건너뛰기·3줄 요약을 이해할 수 있었다.
- [ ] 무음 상태에서도 진행·성공·실패·다음 행동을 알 수 있었다.
- [ ] 새로고침과 저장 export/import 뒤 같은 진행 상태로 복구됐다.
- [ ] 차단 오류가 났을 때 원격 전송 없이 진단 정보를 복사하거나 파일로 받을 수 있었다.

## D1~D3 전체 영업 확인표

- [ ] 영업 준비에서 첫 손님과 추가 손님까지 진행했다.
- [ ] 그릴의 현재 접촉면만 누적되고 임의 시점 반복 뒤집기가 가능했다.
- [ ] 꼬치의 앞·뒤 면을 실제 화면에서 구별할 수 있었다.
- [ ] 공용 완성품을 선택한 뒤 주문이 맞는 원하는 손님에게 제공할 수 있었다.
- [ ] 입장·주문 순서 때문에 유효한 제공이 막히지 않았다.
- [ ] 부분 제공·최종 제공·좌석 정리까지 진행했다.
- [ ] 영업 종료·정산·보상·저장과 다음 날 전환을 완주했다.

## PM 판정 처리

- `PASS`: 정확한 build·URL·asset SHA와 원문 피드백을 epic 완료 증거에 연결하고 다음 consumer를 자동 배정한다.
- `조건부 PASS`: 조건의 owner·수정 경로·재검수 범위를 정하고 최종 `PASS` 전에는 gate를 닫지 않는다.
- `FAIL`: 재현 가능한 결함을 원래 역할 owner에게 배정하고 해당 종속 lane만 멈춘다.
- `실행 불가`: URL·환경·저장·빌드 문제를 먼저 분류한다. 제품 `PASS`나 `FAIL`로 추측하지 않는다.
- 아트·시나리오·실제 소비 화면의 사용자 승인을 PM 또는 QA가 대신 기록하지 않는다.

## 필수 사람 gate

1. S0 상호작용 slice와 S0 전체→D1 전환
2. D1 첫 손님
3. D1 전체 영업→정산→저장→D2 전환
4. D2 전체 영업→정산→저장→D3 전환
5. D3 전체 영업→정산→저장→D4 예고
6. 최초 공개 후보와 이후 스테이지 공개 후보
