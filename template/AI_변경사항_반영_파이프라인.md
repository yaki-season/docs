# AI 변경사항 반영 파이프라인

## 목적

개발 중 또는 개발 후 발견된 변경사항을 `inbox → spec → epic → app` 순서로 일관되게 반영한다.

문서의 변경 이력·날짜·버전은 git을 단일 원본으로 삼는다. 문서 본문에 수동 버전 번호나 `변경 이력` 표를 만들지 않고, 계약 상태는 머리말의 `상태` 라벨로만 표시한다.

```text
사람이 inbox에 미정제 원본 기록
  → AI가 원본 SHA-256 지문 계산
  → AI 분석 및 중복·충돌 확인
  → spec 요구사항 상세 설계 생성·갱신
  → spec/meta에 원본 처리 이력 기록
  → epic 작업 영향 분석
  → 대기·진행 중 작업 갱신 또는 새 작업 생성
  → epic 작업 현황 동기화
  → app에서 구현 및 운영 반영
  → 검증 결과를 epic 작업에 기록
```

## 저장소 경계

| 구분 | `docs` 저장소 | `app` 저장소 |
|---|---|---|
| 사람의 미정제 원본 데이터 | `inbox/`에 원본 그대로 보관, AI 수정 금지 | 참조만 함 |
| AI가 정제한 요구사항 상세 설계 | `spec/`에 작성·갱신 | 참조만 함 |
| 원본 처리 이력 | `spec/meta/`에 작성·갱신 | 참조만 함 |
| 개발자별 작업 계획 | 작성·갱신 | 참조만 함 |
| 게임 소스코드 | 금지 | 작성·수정 |
| 테스트 코드 | 금지 | 작성·수정 |
| 빌드·배포·운영 설정 | 금지 | 작성·수정 |
| 구현 검증 결과 | 요약 기록 | 실제 실행·산출물 관리 |

## 실행 조건

다음 상황에서 파이프라인을 실행한다.

- `inbox/99.change-request/`에 처리 이력이 없는 사람 입력 원본이 추가됨
- 진행 중 작업에서 요구사항 누락 또는 모순이 발견됨
- 구현 완료 후 개선사항이나 결함이 발견됨
- 기획·디자인·아트 기준이 변경됨

## 1단계: 입력 분석

1. `inbox/` 원본을 읽기 전용으로 불러오고 절대 수정하지 않는다.
2. 원본 파일 내용 전체의 SHA-256 지문을 계산한다.
3. `spec/meta/inbox_처리_이력.md`에서 원본 경로와 지문의 기존 처리 여부를 확인한다.
4. 같은 경로라도 지문이 달라졌다면 사람이 갱신한 새 원본 리비전으로 처리한다.
5. 원본의 현상, 원하는 결과, 이유와 영향 영역을 분석 단계에서 분리한다.
6. 관련 `inbox/`, `spec/`, `epic/` 문서를 검색한다.
7. 중복, 충돌, 의존성과 미해결 질문을 확인한다.
8. 정보가 부족하면 추측해 확정하지 않고 판단을 `질문 필요`로 정한다.

## 2단계: spec 갱신

1. 기존 동작과 변경 후 동작을 구분한다.
2. 기능 요구사항과 비기능 요구사항을 갱신한다.
3. 정상 흐름, 예외 흐름, 경계 조건과 완료 기준을 구체화한다.
4. 요구사항 식별자를 유지하고 새 요구사항에만 새 식별자를 부여한다.
5. 근거 `inbox/` 경로와 SHA-256 지문을 연결한다.
6. 처리 판단과 반영 문서를 `spec/meta/inbox_처리_이력.md`에 기록한다.

## 3단계: epic 영향 분석과 반영

모든 개발자 작업에서 변경된 요구사항 식별자와 관련 기능을 검색한다.

| 기존 작업 상태 | 처리 방식 |
|---|---|
| `대기` | 기존 작업의 범위와 완료 기준을 즉시 갱신 |
| `진행 중` | 즉시 갱신하고 `변경 확인 필요`로 전환, 재작업 범위 기록 |
| `변경 확인 필요` | 최신 변경과 참조 요구사항을 반영 |
| `완료` | 기존 문서를 보존하고 새 후속 작업 생성 |
| 관련 작업 없음 | 적합한 개발자에게 새 작업 생성 |

새 작업을 만들 때는 다음을 지킨다.

- 담당 개발자 디렉토리의 가장 큰 순번 다음 번호를 사용한다.
- 하나의 검증 가능한 결과만 목표로 둔다.
- 관련 요구사항 식별자와 문서 경로를 모두 연결한다.
- 선행 작업, 후속 작업과 다른 개발자에게 넘길 입출력 조건을 명시한다.
- 초기 상태는 `대기`로 둔다.

태스크를 갱신하거나 생성한 직후 `epic/작업_현황.md`에서 전체 작업 수, 각 개발자의 현재 작업, 대기·보류·완료 목록을 실제 태스크와 일치시킨다.

## 4단계: app 구현 인계

AI 또는 개발자에게 다음 정보를 제공해 `app` 저장소에서 작업하도록 한다.

```md
목표: [epic 작업의 목표]
참조 요구사항: [spec 경로와 요구사항 식별자]
참조 작업: [epic 작업 경로]
구현 위치: app 저장소
제외 위치: docs 저장소 전체
검증 기준: [epic 완료 기준]
```

구현 중 새 변경사항이 발견되면 사람이 `inbox/`에 미정제 원본으로 기록해 파이프라인을 다시 시작한다. AI는 그 원본을 정리해서 되쓰지 않는다.

## 5단계: 완료 처리

1. `app`에서 구현과 검증을 완료한다.
2. `epic/` 작업에 구현 기준 spec·태스크, 구현 위치, 검증 결과와 남은 위험을 요약한다.
3. 완료 기준을 모두 충족하면 작업 상태를 `완료`로 바꾼다.
4. `spec/meta/inbox_처리_이력.md`에 원본 지문, 판단, 반영된 `spec/`·`epic/` 경로를 기록한다.
5. 처리한 `inbox/` 원본은 변경하지 않고 그대로 보존한다.

## AI 실행 요청 예시

```md
inbox/99.change-request/2026-07-19-손님-대기시간-개선.md를 처리하라.
inbox 원본은 읽기 전용으로 유지하고 수정·이동·삭제하지 마라.
원본 SHA-256 지문을 계산하고 기존 처리 이력과 비교하라.
관련 spec을 갱신하고 모든 epic 작업의 영향을 분석하라.
대기·진행 중 작업에는 변경을 즉시 반영하고, 완료 작업에 필요한 후속 변경은 새 작업으로 생성하라.
epic/작업_현황.md를 실제 태스크 상태와 일치하도록 갱신하라.
처리 판단, 원본 지문, 반영 경로는 spec/meta/inbox_처리_이력.md에 기록하라.
소스코드는 수정하지 말고 변경한 문서와 판단 근거를 보고하라.
```
